## 0. 一句话定位与产品名

**一句话定位**：把「物料」和「人员」在多家供应商的真实价格攒成公司自己的一本底账，勾几行就能出一张带成本和毛利的客户报价单。

**产品名候选**

| 候选 | 含义 | 评价 |
|------|------|------|
| **有底**（首选） | 双关：公司价格底账 + 报价时心里有底 | 两字好记，不撞「XX云」「智慧XX」的模板命名，能直接派生文案（"上次这家做这个多少钱，有底"） |
| 价底 | 直指"价格底账" | 语义准，但读音略生硬，作为对内系统名偏冷 |
| 攒单 | 动作导向，勾选攒成一张单 | 记忆点强、口语化，适合作为报价单模块的功能名，不适合作为系统名 |

**推荐**：系统名「有底」，报价单模块内部动作叫「攒单」。

## 1. 问题陈述

**谁**：5-15 人的活动策划与执行公司里负责报价的人（多为商务/项目经理兼报价员），以及要维护价格的老板或采购。

**什么场景**：客户发来一句"下个月品牌发布会，背景板 6 米、桁架、灯光、主持人、摄影摄像，报个价"。报价的人要在当天甚至半小时内给出一版可谈的报价。

**现在怎么解决**：靠三种方式拼——
1. 微信里翻和供应商的历史聊天记录，翻不到就重新问一遍价；
2. 打开上次类似活动的 Excel 报价单，把单价复制过来（但这些单价是上次的价格，可能已经涨了）；
3. 凭脑子记"上次那家做这个大概两千多"。

**为什么不行**（这是核心，不是"效率低"这么笼统）：
- **价格是散落的、不可检索的**。同一个物料（如 6 米背景板）在不同供应商（线上淘宝 vs 线下定做厂）报价能差 30%-60%，但没人记得住"上次这家做这个多少钱"，每次重新问价，等于每次放弃议价能力。
- **复制旧报价单 = 复制旧价格**。旧 Excel 里的单价是死值，没有生效日期，调价后旧单子还在流通，报出去的价格可能低于当前成本，这一单直接亏。
- **同类人员单价的口径各不相同**。外聘讲师有的按天、有的按场、有的按人天还含差旅，不同供应商口径不同，横向根本没法比，最后只能挑一个"感觉还行"的。
- **报价单本身是手工产物**。物料多的时候一份报价单几十行，靠手工累加、手工加价，错一行整单错；客户改一版搭配就要重拼一遍，改到第五版自己都分不清哪版是最终版。
- **人一离职，价格全丢**。"上次这家做这个多少钱"存在某个人脑子里和微信里，这个人走了，公司的议价历史归零。

**一句话**：真正的痛点不是"缺一个表格"，而是**公司的价格资产没有被结构化沉淀，导致每一次报价都在从零重建**。

## 2. 目标用户

公司内部几个人账号登录共用，电脑网页为主，不做独立 App。

| 角色 | 是谁 | 每天在干什么 | 最关心什么 | 对系统的态度 |
|------|------|--------------|------------|--------------|
| **报价员 / 商务**（主要用户，P0 必须伺候好） | 老板、合伙人、商务专员，1-3 人 | 接需求、当天出报价、被客户反复改单 | 30 分钟内出一版能谈的价；别把成本露给客户；别报错价 | 只要比 Excel 快就用，慢一点就退回 Excel |
| **项目经理 / 执行**（次要用户） | 1-3 人 | 活动现场执行、临时加项改项 | 这个物料哪家有、多少钱、供应商联系方式 | 用得少但关键时刻必须查得到 |
| **采购 / 行政**（价格维护者） | 0-1 人（常由老板兼） | 找供应商、问价、比价、下单 | 一次录一批价要快；谁涨价了；哪家最便宜 | 录价表单每多一个必填字段，录价意愿就掉一截 |
| **老板 / 合伙人**（决策者兼管理员） | 1 人 | 看毛利、定加价率、管账号 | 这单赚不赚钱；成本一年涨了多少 | 只要看板和导出好用就行，不深度操作 |
| **设计师 / 策划**（弱相关） | 1-3 人 | 出方案 | 方案里的物料能不能查到参考图和淘宝链接 | 只读，需要图片和链接 |

**关键洞察**：真正决定这套系统死活的不是老板，是**报价员愿不愿意用**。而报价员愿不愿意用，取决于「出报价单是否比 Excel 快」。所以出单链路必须是主路径，价格库是它的燃料——不能做成"先建库再出单"，那会死在建库阶段。

## 3. 核心用户故事

### 3.1 录物料价（采购 / 管理员）

- As a 采购，I want 给一个物料挂上多家供应商的报价，每家的单价、单位、最小起订量、生效日期都能分开填，so that 下次不用再挨个问一遍。
- As a 采购，I want 同一家供应商同一个物料报 100 份和 500 份两个价，so that 客户加大数量时我能立刻给出阶梯价而不是"我算一下"。
- As a 采购，I want 改价时不是覆盖原价而是留一条新价格记录，so that 我能看到这家从 1800 涨到 2200 的过程，跟它谈的时候有依据。
- As a 采购，I want 给物料传参考图和贴淘宝链接，so that 下次看到名字想不起长什么样时，点开就认出来了，也能直接回到采购源。

### 3.2 录人员价（采购 / 管理员）

- As a 采购，I want 录外聘讲师时能标明是"按天"还是"按场"还是"按人天"，so that 报价时不会把按场的价按天算，差出一倍。
- As a 采购，I want 一个岗位（如主持人）下挂多个具体的人或供应商，每人单价不同，so that 客户预算高低不同时我能换档。
- As a 采购，I want 记录人员单价是否含差旅，so that 异地活动报价不会漏掉这块成本。

### 3.3 查比价（报价员）

- As a 报价员，I want 搜"背景板"就一屏看到所有供应商的当前有效价，最低价自动标出来，so that 我不用问价就能知道这行的行情底线。
- As a 报价员，I want 能切换数量（100 份 / 500 份）看各家对应的阶梯价，so that 客户改数量时我立刻知道成本变多少。
- As a 报价员，I want 搜"背板""KV板""背景墙"也能搜到同一个物料，so that 我不用记住系统里到底叫什么名字。
- As a 报价员，I want 比价时能顺手看到某家这半年的价格走势，so that 我知道现在是高点还是低点。

### 3.4 出报价单（报价员）

- As a 报价员，I want 勾选物料和人员时系统自动按"今天的日期 + 我填的数量"匹配出唯一有效价，so that 我不会用到过期价格或错档的阶梯价。
- As a 报价员，I want 勾选时系统自动取当前最低有效价作为成本，并且允许我手动改选供应商，so that 我既能拿到最优成本，也能按实际要用的那家算。
- As a 报价员，I want 输入加价率（或直接改对客单价）就实时看到这一行的毛利和整单毛利率，so that 我报价时就知道这单赚不赚钱，不用另开一张表算。
- As a 报价员，I want 客户说"背景板换成 8 米"时只改一行，其他不动，so that 我不用重拼整张单，也不用重算全部。
- As a 报价员，I want 生成的报价单是快照，之后供应商调价也不影响这张历史单，so that 客户三个月后拿旧单来问，金额一分不差。

### 3.5 看历史价（老板 / 报价员）

- As a 老板，I want 看到某个物料/人员过去一年各家的价格曲线和涨跌幅，so that 我知道成本在往哪个方向走，加价率该不该调。
- As a 老板，I want 知道哪些价格已经很久没更新过（可能过期），so that 不会拿一个两年前的价去报今天的单。

### 3.6 权限（管理员）

- As a 管理员，I want 只有我能改价格、普通成员只能查和出单，so that 价格不会被误改。
- As a 管理员，I want 成员出单时能看到成本算毛利、但导出的客户版报价单里不出现成本，so that 内部能算账、对外不露底。

### 4.3 替代方案分析（用户现在实际在用的）

| 替代方案 | 它做对了什么 | 它做不到什么（= 我们的不可替代价值） |
|----------|--------------|--------------------------------------|
| **Excel** | 零学习成本、完全灵活、离线、免费、想加一列就加一列 | ① 价格是死值，没有生效日期，分不清"当前有效价"和"去年的价"；② 版本灾难（"报价单-最终版-v3-已确认.xlsx"），无法追溯哪版有效；③ 一个公式拉错一行整单金额全错，且错误不报警——这是报价场景最贵的错误；④ 无法多人同时改，谁改了不知道；⑤ 无权限，成本价和对外价躺在同一个文件里；⑥ 调价后旧报价单被污染 |
| **飞书多维表格 / Airtable / Notion 数据库** | 能建关联表（物料-供应商-价格）、有行/列/视图级权限、有历史记录、有自动化；单表可承载千万行（企业版） | ① **能存不能算**：没有"按当前日期+数量自动匹配唯一有效价"的原生能力，要靠复杂公式/自动化硬凑，而"公式报错了都不知道问题在哪"是被反复吐槽的点；② 没有"阶梯价按数量自动升档""多供应商自动标最低""勾选即校验数量未达起订量"这类业务规则，全靠人记；③ 出报价单是最后一公里——排版打印要付费、要手工，且无法保证快照；④ 权限只能到表/行/列，做不到"成员出单时能读到成本算毛利、但导出时不出现成本"（计算但不可见）；⑤ 免费版单表有行数上限（公开资料有 2000 条 / 5000 条两种说法，以官网为准），企业版按成员数计费，被用户评价为"大公司看不上，小公司用不起"；⑥ 本质是协作工具不是业务系统，用户反馈"数据量超 5 万行或流程复杂时性能骤降"、且"要求用户先具备系统设计思维，普通用户学一两周仍不会设计表"——小公司没人干这个活 |
| **微信群** | 即时、零成本、供应商就在里面 | 价格沉在聊天记录里，不可检索、不可比价、不可出单；人一离职全部归零；同一个物料三次问价得到三个数字，没有任何地方能对齐 |

### 4.4 从差评里提炼的市场空白（5 条）

1. **方向错位**：行业现有工具都在做「我向供应商询价」（采购侧/平台侧），没人做「我方对客户报价时，立刻知道各家成本 + 毛利」（销售侧/企业自有资产侧）。价格数据必须留在公司自己手里，不能变成平台的资产。
2. **太重**：为了"记住上次这家做这个多少钱"这一个诉求，要上一套项目/合同/预算/审批/财务的 ERP。行业评测已经给出失败模式：「员工嫌复杂不愿用，最后工具闲置」。小公司需要的是能用起来的 10%，不是用不起来的 100%。
3. **进销存的价格模型撞墙**：管家婆这类产品价格体系确实最深，但它要求"存货 + 库存 + 单据流"。活动物料是一次性定制/租赁/按㎡，人员根本不能当存货——价格维度（按天/按场/按人天、含不含差旅）直接撞墙。
4. **通用表格能存不能算**：有效期自动失效、阶梯价自动升档、比价自动标最低、勾选生成带毛利的报价单——这四条恰恰是多维表格要靠人肉公式硬凑的部分，而人肉公式出错不报警，正是报价最不能承受的错。
5. **出报价单这最后一公里没人做好**：要么手工排版（多维表格/Excel），要么只能对标准目录价（小程序类）。"多供应商成本 → 快照报价单 → 不露成本"这条链是断的。
6. **附件的场景被低估**：物料是"看图认物"的，淘宝链接就是采购源。进销存/ERP 的物料档案重编码规格，不重"点开链接回到那家店"。

## 5. 我们的差异化

**用户为什么选我们，而不是继续用飞书多维表格 / Excel？**

一句话：**因为报价出错和报价慢是会直接丢钱的，而多维表格和 Excel 只能帮你"记下来"，帮不了你"算对"和"出得快"。**

三条硬差异（可被验证，不是形容词）：

| 差异 | 具体能力 | 多维表格/Excel 为什么做不到 |
|------|----------|----------------------------|
| **价格会自动"对"** | 价格带生效期 + 数量阶梯。出单时系统按"今天 + 数量"自动匹配唯一有效价，过期价自动不出现，阶梯自动升档 | 这是业务规则，不是公式。要靠多重 IF + TODAY() 手写，一列写错全表失效且不报警 |
| **比价一屏看完** | 一个物料横向列出所有供应商当前有效价，最低价自动标注，可切数量档看阶梯 | 需要手工做透视或多表拼接，加一个供应商就要改表结构 |
| **成本算得清、对外露不出** | 出单时实时显示成本/对客价/毛利/毛利率；导出客户版自动剔除成本列；报价单生成即快照 | 多维表格无"计算但不可见"权限，成本和对客价只能放同一个表里靠人删列 |

**反向定位（同样重要）**：我们不跟用友畅捷通 / 自由超越比功能全。它们是 ERP，我们是**一本账 + 一台出单机**。明确告诉用户：这里没有审批流、没有项目成本核算、没有财务集成——因为你们公司 10 个人，上了那些反而没人用。

**版本化规则（必须写进实现）**：
- 改价 = **新建一条 PriceBook**，同时把旧条目的 `effective_to` 设为新条目 `effective_from` 的前一天（或按用户指定），旧条目 `status = superseded`。**禁止原地 UPDATE unit_price**。
- 这是「历史价格趋势」能成立的前提，也是"客户拿三个月前的报价单来问，金额一分不变"的基础。

**唯一性约束是六元组，不是四元组（v1.3 增两维，v1.4 再增一维）**：
唯一性作用于 `(item_id, supplier_id, pricing_nature, tax_included, pricing_mode, 生效期区间)`。

- `pricing_nature`：不带的话，同一 LED 屏的买断价与租价无法共存，**用户会被迫给租赁商建假供应商** —— 模型逼用户污染数据。
- `tax_included`：不带的话，"开票价 / 不开票价"只能砍掉一个塞进自由文本备注（见 6.6.3）。
- `pricing_mode`（仅人员取值，物料恒为 NULL）：不带的话，同一讲师无法同时记"按场 2800"与"按天 1500"（见 6.6.1 末段）。物料侧不设此维，因为物料的单位差异属于可折算的计量差异，不是不同产品。

**两层的分工（v1.5 修正）**

我原先写"约束必须放应用层，不得做成数据库唯一索引"——**这句话过绝对，把手段当成了目的。**

真正的目的是：**用户永远不该看到数据库异常。** 而实现这个目的，靠的是"应用层先校验 + DB 约束兜底 + DB 异常被捕获翻译"，不是"不要 DB 约束"。

| 层 | 职责 |
|----|------|
| **应用层校验** | 常规路径给出**可读的业务提示**（"已被他人创建同生效日的价格"） |
| **DB EXCLUDE 约束** | **兜底**：防手工导数据脚本绕过、防两个请求同时通过应用层校验的竞态穿透 |
| **异常翻译** | 应用层捕获 `23P01`，翻译成同上那条可读提示。**响应体任何位置不得出现 `23P01` / `constraint` / `violation`** |

为什么必须有 DB 兜底：架构师的原话成立——**只靠应用层自律，第一个写脚本导数据的人就会破坏它**。而历史价格版本化一旦被破坏，趋势图和历史报价单都跟着失真，且**破坏之后没有任何报错**。

> 这条同时说明一个通用判断：当一个约束涉及"数据不变量"（invariant）时，**应用层负责体验，数据库负责正确性**。只要两者都在，就不会出现"用户看到技术异常"或"脚本悄悄破坏不变量"。

### 6.3 关键建模决策（需架构师确认）

**决策 A：物料与人员合成一张 `PricedItem` 表，用 `item_type` 判别；分类树分两个 domain。**

- **理由**：三条核心链路——多供应商比价、历史价格趋势、勾选进报价单——在物料和人员上的逻辑**完全一致**。若拆两张表，报价单明细要做多态关联，比价页要写两套查询，趋势图要写两套聚合，架构和前端成本接近翻倍，且后续加第三类计价主体（如"场地"）要再翻一次。
- 差异用「可选字段组」承载：物料的 `spec`/图片链接；人员的 `pricing_mode`/`includes_travel`。
- 隔离靠 `Category.domain` 保证，不让"主持人"混进"物料/搭建"树。
- **风险**：单表字段会有稀疏（人员不用 `moq`，物料不用 `pricing_mode`）。可以接受——字段少，且表单按 `item_type` 动态渲染即可。
- **备选方案（如架构师否决）**：保留 `PricedItem` 为抽象主表，`Material`/`Personnel` 为扩展子表，`PriceBook` 只关联主表。这样也能避免价格逻辑重复，代价是多一层 join。

**决策 B：价格版本化，改价 = 新增版本，禁止原地覆盖。**

- **理由**：这是「历史价格趋势」和「报价单快照」两个用户已明确要求的共同底座。若允许覆盖，趋势图无数据源，历史报价单会被污染。
- **实现要求**：需要一个"某主体 × 某供应商 × 某日期 → 唯一有效 PriceBook"的解析函数，且必须处理**日期区间重叠**的冲突（见风险项）。

**决策 C：报价单明细存快照，不只存外键。**

- **理由**：客户三个月后拿旧单来问，必须一分不差。同时"这个物料历史被报过几次/平均报多少"也需要 `item_id` 弱关联，所以是"弱关联 + 全量快照"而非纯快照。

**决策 D：单位做成枚举表，不做自由文本。**

- **理由**：单位决定数量语义。自由文本会出现"米/延米/m/延米（含安装）"四种写法，比价和汇总全废。

### 6.4 单位与计价方式枚举

**物料单位**：`个` / `件` / `块` / `张` / `套` / `组` / `根` / `卷` / `㎡`（平方米）/ `延米` / `m`（米）/ `天`（租赁按天）/ `场` / `批`

> `根`、`卷` 是为桁架（按根）、地毯/布幔（按卷）补的。跨单位比价依赖 6.6.2 的折算系数，不靠单位本身换算。

**人员计价方式**：`per_day`（按天）/ `per_event`（按场）/ `per_person_day`（按人天）/ `per_hour`（按小时）/ `per_half_day`（按半天）

**三个名字各指一件事，不要混（v1.8 补，设计与架构之间已出现混淆）**

| 名字 | 落在哪 | 取值 | 含义 |
|------|--------|------|------|
| `unit_code` | `prices.unit_code` / `items.base_unit_code` | 短码：`day` / `session` / `person_day` / `hour` / `half_day` / `个` / `张` / `㎡` … | **计量单位本身** |
| `unit_mode` / `pricing_mode` | `prices.unit_mode`（生成列）/ `items.pricing_mode`（派生） | 带前缀：`per_day` / `per_event` / `per_person_day` / `per_hour` / `per_half_day` | **业务口径**，由 `unit_code` 一一映射而来 |

映射固定：`day→per_day`、`session→per_event`、`person_day→per_person_day`、`hour→per_hour`、`half_day→per_half_day`。

**`unit_mode` 的取值域只有这 5 个，非时间类单位一律是 NULL（v1.9.2 定死，OD-17）**

不要给所有单位派生 `per_<unit_code>`（`per_sqm`、`per_sheet`、`per_piece`…）。缺了这个限制会坏两件事，而且都不报错：

1. **EXCLUDE 会允许同一供应商同期并存 "㎡ 价" 与 "张 价"** —— 而它们其实是同一个价的两种写法。取价于是回到"取决于执行计划挑了哪条"，这是最坏的一种不确定性。
2. **`resolvePrice(unit_mode = NULL)` 会把所有物料价滤掉** —— 物料行的传参就是 NULL（"只取非时间口径"），而 `per_sqm ≠ NULL`，比价页会整页空白。

**"按㎡报价"与"按张报价"要并存，正确做法是同一条价填 `base_unit_qty` 做折算**（机制见 6.6.2），**不是加第六维**。加维度看起来更"支持"，实际是把一个可折算的计量问题升级成不可比的分类问题 —— 而 6.6.2 已经说过：物料的张/㎡是同一产品的不同计量，人员的场/天才是两个不同产品。

**这不是两套名字，是两个字段 + 一张固定映射表。** 接口和埋点里必须统一：**存单位用短码，表达业务口径用带前缀的 `per_`**。两边各写一套会在联调时变成必现 bug —— 而且因为它"看起来只是命名"，排查时最费时间。

（三个名字已定，R16 于 v1.9.2 结案，架构师逐字确认。）

> **MVP 简化说明**：`per_person_day`（按人天）在语义上数量 = 人数 × 天数，但 MVP **不自动换算**，由用户在数量里直接填结果（如 3 人 2 天填 6），单位显示为"人天"。自动拆分人数/天数字段列为 P2，理由见 Out-of-Scope。

### 6.5 分类种子（供设计师出信息架构）

> **强制约束**：分类必须是**两棵树**（物料树 / 人员树），依据 `Category.domain` 隔离。**禁止把人员和物料放在同一个一级导航下**——「演艺人员」和「印刷物料」并列会导致 `item_type` 判别失效、比价页与出单侧栏无法按类型过滤。这一条无例外。
>
> **命名原则**：用行业口语，不用规范书面语。用户天天点这一层，用错词会被说"不专业"。以下命名采纳了设计师提供的行业说法（舞美硬体 / 灯光音响 / 桌椅布草 / 演艺资源 / 美陈 / AV 设备），比初版更接近客户语言。
>
> **种子只是初始值**：全部可增删改名、可拖拽排序。**用错词的代价必须由"可改"来兜底，而不是靠我们猜对**。管理员首次登录引导里要明确提示"分类可以按你们自己的叫法改"。

### 6.6 计算与比价口径定义（下游必须按此实现，不得自行解释）

> 这一节是给设计师和架构师的**唯一口径来源**。设计稿、接口、PDF 模板、提示文案全部以此为准。

#### 6.6.1 交易性质：比"单位"更容易出错的一个维度

同一个物料存在三种完全不同的价格，混在一起标最低价会造成报价事故：

| nature | 含义 | 例子 |
|--------|------|------|
| `purchase` | 买断 | 淘宝买一块 LED 屏 8,000 元 |
| `rental_per_day` | 按天租赁 | 租赁商 LED 屏 500 元/天 |
| `custom_made` | 定制加工 | 定做厂桁架背景板 1,200 元/套（含画面） |

**规则**：**最低价只在同一 `pricing_nature` 内比较**。租价和买断价放在一起比，会得出"租赁商最便宜 500 元"这种结论——按这个价报一个需要买断的活动，一单亏几千。

**展示规则**：比价页按 nature 分组成段（"买断价" / "租赁价·按天" / "定制加工价"），每组各自标最低。不跨组标最低，不跨组排序。

**默认值**：`purchase`。若该物料的供应商类型是 `rental`，录价时自动预填 `rental_per_day` 并高亮提示确认。

**人员也需要分组，且是同一个事故（v1.4 补，设计师发现）**

我原来只把 `pricing_nature` 用在物料上，认为"人都是租"。**这个判断是错的**：人员有 `按场 ¥2,800` 和 `按天 ¥1,500` 两种计价方式，混在一列标"最低 ¥1,500"，跟 LED 屏买断/租赁是**完全同一种事故** —— 一场活动报价员按"按天"的价报了"按场"的活，一单亏一半。

两者性质相同但成因不同：物料的差异在"买还是租"，人员的差异在"按场还是按天还是按人天"——**后者不是计量单位不同，是交付量不同**（一场可能包含三天，也可能只是一次上台）。

**规则**：
- 人员的比价按**该条价格实际使用的计价单位**分组成段（不是按主体的默认计价方式），组内标最低，跨组不比较
- **`unit_mode`（由价格行的 `unit_code` 派生）必须进唯一性键**（作为第六维）。否则同一讲师 × 同一供应商无法同时存在"按场 2800"和"按天 1500"两条价 —— 用户又会被迫造假
- 自检第 3 条（成本高于最低价）必须限定**同性质 + 同税口径 + 同计价方式**，否则会拿按天的价去劝按场的单"你贵了"

**分组基准必须是「这条价格的计价单位」，不是「主体的默认计价方式」（v1.8 修正，架构师指出的错）**

我原先写的是"按主体的 `pricing_mode` 分组"。**这个基准会标错组**，架构师给了个反例：

> 一个 `base_unit = 人天` 的讲师，A 经纪按**场**报 2800。
> 该讲师的**主体**默认计价方式是"按人天"，但**这条价格实际按场**。
> 若按主体的默认方式分组，A 这条 2800 会被归进「按人天」组，与别人的「按人天 1500」一起标最低 —— **又回到了这次要修的那个事故。**

所以正确基准是：**`prices.unit_code`（该条报价实际按什么单位计价）→ 派生出 `unit_mode`**，而不是 `items.base_unit` 派生的主体默认方式。

两者**可以不一致，而且这不是数据错误**——同一个讲师被不同供应商用不同方式报价是现实（经纪公司按场、个人按天）。

**这个改法对物料侧的连带影响（是改善，不是退步）**：物料的时间类单位也会按口径细分——同一桁架「按天 500」与「按场 3000」会被分成两组而不是混排。这恰恰是对的：**"一场"包含几天不在价格里，所以按天和按场本来就不可比**，与人员是同一个道理。

非时间类单位（个/张/㎡/套/根/卷）的行为零变化——它们先经折算系数归一到 `compare_unit`，再参与比较。

> **实现约定**：物料侧的 `unit_mode` 维度必须**恒为同一个值**（不参与区分），这样唯一性对物料就退化为 `(主体, 供应商, 性质, 税口径, 时段)` —— 即"一个物料在一个供应商下只保留一条价，单位差异用折算系数解决"。只有人员侧这一维才真正起区分作用。

> 为什么物料的单位差异不单独做一维、而人员的计价方式要做：物料的「张 vs ㎡」是**同一产品的不同计量**，可以用折算系数统一；人员的「按场 vs 按天」是**两个不同的商业产品**，无法折算（一场包含几天的信息不在价格里）。这是两者必须区别对待的原因。

**列表页的"最低价"列也必须按性质/计价方式拆开（v1.4 补，设计师发现）**

物料库和人员库的列表页，如果给一个多性质的条目显示一个 `最低 ¥380`，后面跟着 ¥8,000 的买断价，**这是全站最容易造成错单的一格** —— 比比价页更危险，因为列表页没有上下文，用户看到 380 就按 380 记忆了。

规则：
- **只有一种性质/计价方式时**，才显示单一最低价（正常情况，占多数）
- **有多种时**，必须把性质和价格绑在一起显示（如 `租 ¥380/天` + 一个角标提示有 2 种性质），不能只给一个裸数字
- 禁止出现"跨性质取 min 后只显示数字"的任何形态

这条同时适用于：物料库列表、人员库列表、搜索结果、报价单勾选侧栏、以及任何"最近查看/常用物料"式的摘要卡片。

**自有人员也要录价，但语义不同（v1.7 补）**

用户在需求里明确提到人员有「**自有管理人员 / 外聘专家 / 外聘兼职**」三类。这意味着「自有人员」也必须有一条价格 —— 否则"这个活用自己人做，能省多少"这个问题无法回答，而这正是用户要的对比。

**但自有人员的价格语义是"内部成本折算"，不是"付给供应商的钱"：**

| 供应商标识 | 价格含义 | 报价时是否发生真实支出 |
|---|---|---|
| `freelancer` 外聘兼职 / 经纪公司 | 付给对方的钱 | 是 |
| `internal` 自有员工 | **内部成本折算**（如日薪 + 社保摊销），不是对外支付 | 否（是机会成本） |

**两条实现与文案要求**：
1. 录 `internal` 类型人员的价格时，字段提示必须写明「这是内部成本折算，不是对外支付」。否则用户会以为自己要给别人打钱，或者反过来 —— 老板看到"自己人还有成本"会觉得系统算错了。
2. 比价时 `internal` 与 `freelancer` **同组可比**（同计价方式下），因为用户要的正是这个对比；但卡片上必须显示供应商类型标签（**自有 / 外聘**），否则会得出"自己人比外聘贵"这种没头没尾的结论 —— 用户需要看见"贵"的是自有人员折算成本，而不是在比两个外聘报价。

> 一个连带的好处：这个对比在现有模型里**不需要新增任何字段**。`supplier.type` 已经区分 `freelancer` / `internal`，两条价各自挂在自己名下，比价页天然就并列显示。用户 Phase 0 提到的三类人员口径，靠 `supplier.type` + `pricing_mode` 两个维度就装下了。

**`pricing_nature` 的默认值来自分类，人员恒为 `service`（v1.8 定稿，客户 Q2 口径）**

客户的回答解决了 R10：**设备器材类以租赁为主**。落地方式：

| 类别 | 默认 `pricing_nature` | 客户原话对应的例子 |
|---|---|---|
| 设备器材 | `rental_per_day` | LED 屏、音响、灯光、桌椅、投影、发电机、空调 |
| 定做加工 | `custom_made` | 桁架、背景板、喷绘、KV 板、礼品定制 |
| 标品采购 | `purchase` | 伴手礼、饮用水、耗材 |

**默认值由分类继承（6.5 每个一级分类带一个），逐条可覆盖。**

为什么不设"全局默认 `purchase`"：按分类带默认时，**录价时 90% 的情况不用选**；而一个错的全局默认会让另外 90% 的人每次都要改一次 —— **每次都改的默认值等于没有默认值，而且比没有更烦**。

**人员的 `pricing_nature` 恒为 `service`，不用 NULL。**

这不是洁癖，是一个会静默失效的技术坑：`pricing_nature` 在唯一性键里，**如果人员取 NULL，唯一性就整段失效** —— SQL 里 `NULL = NULL` 不成立，两条完全重复的人员价不会被约束挡住，也不会报错。**错误会变成"两条价并存、系统随便挑一条用"**，属于最难查的那一类。所以枚举增第四值 `service`，`NOT NULL`，人员恒取该值、不给用户选。

**这同时保证了"最低价只在同性质内比较"对人员也成立**：人员只有 `service` 一种性质，比价分组因此完全由 `unit_code`/`unit_mode` 决定（6.4），两个维度不打架。

#### 6.6.2 跨单位比价：折算系数，不做全局单位换算字典

**决策：不做全局单位换算字典（拒绝"喷绘 12 张/㎡、LED 1 块 = 0.25 ㎡、桁架 1 根 = 3 m"这类全局表）。**

理由三条：
1. 这些系数**不是行业常量，是每个物料各自的包装/规格事实**。"12 张/㎡"只对某个克重的喷绘布成立，换个克重就变；"1 根 = 3 m"只对某个规格的桁架成立。做成全局字典必然错。
2. 活动物料里大量是「1 套 = 一堆东西」（如"签到台套装"），客观上**无法换算**。一个宣称能换算所有物料的字典是在骗用户。
3. 建单位换算图（量纲、基准、链式折算）是一个独立子系统，MVP 不该背。

**采用的方案：折算系数录在价格条目上，选填。**

- `PricedItem.compare_unit`：管理员给该主体指定一个比价基准单位（如"㎡"）。**只在同一主体下各供应商单位不一致时才需要填**。
- `PriceBook.base_unit_qty`：1 个比价基准单位 = 多少个本价格单位。
  - 喷绘布，基准=㎡，淘宝按张、12 张/㎡ → `base_unit_qty = 12`
  - LED 屏，基准=㎡，租赁按块、1 块 = 0.25 ㎡（即 1㎡ = 4 块）→ `base_unit_qty = 4`
  - 桁架，基准=m，按根、1 根 = 3 m（即 1m = 1/3 根）→ `base_unit_qty = 0.3333`
- **折算单价 = `unit_price` × `base_unit_qty`**（乘，不是除。除数容易算错方向，实现时请注意）。

> **字段命名与录入口径**：DB 字段统一叫 `base_unit_qty`，不叫 `conversion_factor`。原因是 "factor" 存在方向歧义（是乘还是除说不清），而这正是最容易写反的地方。**录入界面上不要出现"换算系数"这个词**，改用问句：「1 ㎡ = 多少张？」「1 m = 多少根？」—— 问句天然消除方向歧义，用户按自己的说话方式填就行。

**两条防守规则（v1.3 补，均为架构师提出或补充）**

1. **`base_unit_qty` 必须可空，禁止 `NOT NULL DEFAULT 1`。** 因为"没填"与"填了 1"语义完全相反：前者是"我不知道，不可比"，后者是"我断言 1 个基准单位等于 1 个本价格单位"。用默认值 1 会把所有"未填"静默变成"谎称单位一致"，这是最坏的一种默认值——它让错误看起来像正确。
2. **当 `unit ≠ compare_unit` 但 `base_unit_qty = 1` 时，拒绝保存。** 这在逻辑上恒为错：如果两个单位真的是 1:1，那就应该把 `unit` 直接改成 `compare_unit`，而不是用一个系数声明它们不同名却等量。允许它存在只会制造"看起来填了系数、实际没换单位"的脏数据。

**给客户的取数口径（并入 Q1）：要整数，不要小数**

最好是让客户填「1 个比价基准单位 = ? 个某家的单位」这样的整数。判断 `compare_unit` 选得对不对，有个极简的自纠规则：

> **如果客户给出的答案是小数（比如 1 ㎡ = 0.2 卷），说明 `compare_unit` 选反了 —— 换成另一个单位（卷），答案就变成整数（1 卷 = 5 ㎡）。**

这条规则让"选哪个单位做基准"不再需要产品经理拍脑袋，而是由数据自己决定：**能得出整数的那个方向就是对的**。同时它保证了全项目只在录入边界做一次乘法，任何地方都不出现除法。

按此规则预判几个常见物料（待客户确认）：
- 喷绘布：`compare_unit = ㎡`，淘宝按张 → 1 ㎡ = 12 张（整数）
- 桁架：`compare_unit = 根`，按 m 的供应商 → 1 根 = 3 m（整数）
- 地毯：`compare_unit = 卷`，按 ㎡ 的供应商 → 1 卷 = 50 ㎡（整数）
- LED 屏：`compare_unit = ㎡`，按块 → 1 ㎡ = 4 块（整数）
- 「1 套 = 一堆东西」类：**无解，填不了，走规则 3（不可比）** —— 这是正常结果，不是缺陷

**比价规则（三级）**：
1. 单位一致（`unit` = `compare_unit`）→ 直接参与最低价计算。
2. 单位不一致但填了 `base_unit_qty` → 折算后参与，卡片显示「折算 60 元/㎡（原 5 元/张）」。
3. 单位不一致且未填 `base_unit_qty` → **不参与最低价计算**，排在已折算行的后面，显示琥珀提示「未折算，不能比」。仍可见、仍可加入报价单（按原单位）。

> 这把设计师提的"单位不一致的行不参与最低价"从"一刀切"细化为"未折算才不参与"。对用户更友好，且成本只多一个选填字段。

**冷启动依赖**：`base_unit_qty` 是客户业务事实，我们无法凭空填。**必须向客户索取约 10 个高频物料的真实折算关系**（喷绘布、KT 板、桁架、LED 屏、地毯、桌椅、易拉宝优先）。拿不到就退化为规则 3——功能降级但不崩，只是"最低价"覆盖度变低。

#### 6.6.3 含税/不含税：两个口径**允许并存**，比价按口径分组

**MVP 不采集税率，只记 `tax_included` 布尔。**

**关键决策（v1.3 修正）：同一主体 + 同一供应商 + 同一交易性质 + 同一时段，允许同时存在「含税」和「不含税」两条价格。**

我最初写的是"跨税口径不标最低价"，隐含"两者可以并存"。架构师提出改成**不允许并存**，理由是：一旦允许，`resolvePrice()` 就不再单值，出单时无法自动取成本，用户每次都要手动二选一。

**我不采纳这个改动，因为它砍掉的是一个真实且高频的业务事实。**

活动行业里，同一个供应商同一个物料同时报两个价是常态：**"要票 3200，不要票 2900"**。淘宝个人卖家多数不开票，厂里报价默认不含税、要票加点。客户这单要不要发票，取决于甲方是公司还是个人、是否走对公流程。所以：

- 砍掉一个口径，等于逼用户把另一个价塞进 `source_note` 自由文本 —— 价格库就漏了一格，且不可计算；
- 用户真的需要"这单要票/不要票"两个成本，砍掉之后他只能在下单时凭记忆手算，**而这正是这套系统要消灭的行为**。

**架构师担心的"不单值"问题可以解掉，且成本很低：**

`resolvePrice(item, supplier, pricing_nature, date, qty, tax_basis)` —— 增加一个 `tax_basis` 入参，返回仍是**单值**。而 `tax_basis` 不需要新概念：**报价单本身已经有口径声明了**（见 6.6.9，每张单声明"以上报价为含税价/不含税价"），出单时直接用本单的声明口径取成本，用户零操作。

**比价规则（替代原方案）：**
- 比价结果按 `tax_basis` 分组返回；或按当前报价单口径只显示同口径的行
- **不同口径之间不标最低价、不排序、不标并列**，显示「税口径不同，不能直接比」
- 同口径内正常比价

**为什么不用"统一折算成含税比"**：MVP 没有税率，无法把不含税价反算成含税价。举例：A 报不含税 100、B 报含税 105。按不含税比 A 便宜，按含税比 B 便宜（A 含税 113），**结论直接相反**。而**给出一个错误的"最低价"比不给最低价危险得多**——用户会照它下单。

这与 6.6.2 的处理逻辑同构（口径不同 → 不参与比较），用户只需理解一条规则："口径不一样的东西，我不给你标最低，但我都给你列出来。"

**「列出来」这三个字是硬约束（v1.5 补，架构师发现的边界）**

同组里若甲方、乙方、丙方都报了含税价，而**丁只报了不含税价**——按本单口径（含税）过滤后，丁会从列表里消失，前端显示成「丁没报价」。**这是错的**：丁有价，只是口径不同，而"这家有货但不能直接比"本身是有用信息。

规则：
- 不同口径的行**不过滤掉**，仍作为该组的一行返回，标记为不可比 + 原因 `TAX_BASIS_MISMATCH_ONLY`
- 前端展示必须点明"有价但不能比"（如「丁 仅报不含税 2900，不能与含税价直接比」），不能让用户以为它没报价
- 「无报价供应商」清单只放**完全没有任何价**的供应商

> 统一成一句话，适用于本 PRD 里所有"口径不同"的场景（单位未折算、跨税口径、跨交易性质、跨计价方式）：
> **凡是"存在但不可比"的行，一律留在列表里并标记，绝不静默删除。** 静默删除会让用户永远想不起来去补那个口径。

**约束上的配套**：`tax_included` 必须进唯一性五元组（见 6.2），否则两条价插不进去。

`tax_rate` 字段列为 P1：加上之后才支持按含税口径统一比价与税额拆分。届时需向客户确认常用税率档（小规模纳税人 3%/1%、一般纳税人 13%/6%）。

> **需要客户确认（并入 Q7）**：你们报价时，同一个物料会不会同时记"要票"和"不要票"两个价？
> - 会 → 按本节并存方案
> - 不会（只记实际采用的那一个）→ 架构师的简化方案也可行，成本更低
>
> **但无论客户怎么答，唯一性五元组都建议带上 `tax_included`** —— 它只是唯一键多一维，零成本，却能把将来放开的路留着。去掉一维将来要迁移，加上一维永远不亏。

#### 6.6.4 价格状态四级：硬失效与软陈旧必须分开

**这是最容易被混为一谈、且直接导致报价事故的地方。设计师的设计稿里把两者合并成"过期"，需要拆开。**

| 级别 | 判定条件 | 颜色 | 行为 |
|------|----------|------|------|
| 有效 | 今天在 `[effective_from, effective_to]` 内，且距 `max(updated_at, last_used_at)` ≤ 阈值 | 正常（无标记） | 正常参与比价与出单 |
| **软陈旧** | 有效期内，但距 `max(updated_at, last_used_at)` > 阈值 | 琥珀 + 文字「(!) 187 天未核价」 | **仍参与**比价与出单；不阻断、不弹窗；仅工作台"待处理"计数 |
| **硬失效** | `effective_to` < 今天 | 灰（历史）/ 红（出单时） | **不参与**比价；出单时命中红色「无有效价，请手填成本」 |
| 被替代 | `status = superseded` | 灰 | 只出现在历史趋势，不参与比价 |

**关键设计点：软陈旧的计时起点是 `max(updated_at, last_used_at)`，不是单纯 `updated_at`。**
一个价格虽然 187 天没改过，但上周刚被用在报价单里且客户没投诉，说明它大概率还有效——这时提醒它"过期"是噪音，会让用户对提醒脱敏，最终所有提醒都被忽略。所以只要被用过就重置计时。

**`last_used_at` 的回写方式（v1.3 修正：同步，不做异步）**

我最初建议异步/延后批量更新，架构师指出这是过度设计，我认同。理由：这是同库单表按主键更新，影响行数 = 单张单的行数（上限 50 行），1ms 量级；而异步要引入队列或定时任务，还要兜"异步失败后没写上"的不一致。**最终一致适用于跨服务，不适用于同库同事务的两条 UPDATE。** 同步放在 `issue` 事务内即可。

**但有一处必须钉死：回写 `last_used_at` 绝不能顺带修改 `updated_at`。**
`updated_at` 的语义是"这个价格被改动过"，它支撑审计与历史趋势。如果出单时被顺带刷新，后果是：① 审计日志里每一笔出单都显示成"价格被修改过"，真正改价的动作被淹没；② 历史趋势图会把"被使用"误读成"被调价"，图形彻底失真；③ 软陈旧判断虽然靠 `GREATEST` 兜住了，但上面的两个问题它兜不住。

实现要求：`UPDATE prices SET last_used_at = now() WHERE id IN (...)`，**只动这一个字段**，不要用 `updated_at = now()` 的全量更新模板。

**阈值**：默认 **90 天**，全局统一，**MVP 不按分类设多套阈值**。理由：MVP 阶段先让用户建立"价格会变旧"这个意识；按分类配阈值是配置负担，且我们没有真实数据支撑"哪个分类该几天"。列 P2，等有 3 个月使用数据再定。

若客户反馈 90 天太吵：调成 180 天，一行配置的事。但要提醒客户——调长意味着更可能拿旧价报价，这是明确的风险权衡。

#### 6.6.5 毛利率口径

- 行成本小计 `line_cost` = `cost_unit_price` × `qty`
- 行报价小计 `line_price` = `sale_unit_price` × `qty`
- 行毛利 `line_profit` = `line_price` − `line_cost`
- 整单成本合计 = Σ`line_cost`
- 整单报价合计 = Σ`line_price`
- 整单毛利 = 报价合计 − 成本合计
- **整单毛利率 = 整单毛利 / 整单报价合计**（分母是**报价**，不是成本）

> 确认设计师的表述正确。作为对照：成本加成率（markup）= 毛利 / 成本，与毛利率是两个不同指标。

**但"不出现加成率"不够 —— 用户嘴上一定会那么说（v1.4 补，设计师提出的改进）**

我原来只写了"系统内一律只用毛利率，不出现加成率"。**这个规定只治了界面，没治用户的脑子。**

报价员说"这个我加 40 个点"，他指的是**成本 × 1.4**，对应的真实毛利率只有 **28.6%**。而系统里存的是毛利率（售价 = 成本 ÷ 0.6，即成本 × 1.667）。**两个数差 11.4 个百分点 —— 一张 10 万的单差一万多。** 界面把"加价率"三个字藏起来，并不会让报价员停止用这个说法，只会让他在心里换算，然后填错。

**采用的做法：统一叫「毛利率」，并在输入框旁边常驻一行实时换算，直接承认用户的说法。**

示例（用户输入 40 时实时显示）：
> `毛利率 40% → 对客价 = 成本 × 1.667`
> `若你指的是"成本加 40 个点"，那对应毛利率 28.6% —— 这里填的是毛利率`

这一行必须是**常驻可见的辅助文字**，不要藏在 popover 里。理由是：会造成错误的那一瞬间就是他输入数字的那一瞬间，藏在弹层里的解释等于没有。

**P1 候选**：如果实际使用中报价员反复抱怨"我们习惯说加几个点"，再考虑把输入框做成"毛利率 / 加价率"双模式（带明确的模式切换，且两者实时互相显示）。MVP 不做双模式，因为一张报价单上只能有一个口径，两个数同时摆在页面上反而会让老板看错。

**预警阈值：按项目类型配置，不写死一个数（v1.9 定案，客户 Q3）**

原先只有一个全局 25%。客户答复后改为**按项目类型分档**，阈值存配置表（`margin_thresholds` 或 `app_settings` 的等价结构）：

| 项目类型 | `project_type` | 默认预警线 |
|---|---|---|
| 年会 / 庆典 | `annual_event` | 30% |
| 品牌发布会 | `launch_event` | 30% |
| 展台特装 | `exhibition_booth` | 25% |
| 路演 / 地推 | `roadshow` | 20% |
| 长期框架客户 | `framework_client` | 15% |
| **（项目类型为空）** | `null` | **25%（全局默认）** |

- **取值顺序**：`quotes.project_type` 有值 → 查该类型的阈值；为空 → 全局默认 25%。
- **这套数字是占位默认值，不是客户的事实。** 设置页必须明写一行：「以下为初始值，请按你们实际的安全毛利线修改」。上一版的教训是阈值写死会让人麻木，这一版的教训会是"看起来像我们定的"——所以文案比数字重要。
- 行级仍不设阈值，只显示数值（每行加价策略天然不同，有的物料走量只加 5%）。
- 整单毛利率 < 该单类型的阈值 → 汇总条变琥珀（不是红色，避免狼来了）。
- 整单毛利 < 0 → 红色强提示「这单是亏的，确认出单？」。
- **[硬约束] 预警线只影响两处：提醒颜色 + 自检第 2 条。永不拦截出单。** 这条在 v1.7 已钉死，新表不许破 —— 一旦按类型配置了阈值，很容易有人顺手做成"低于线不给发"，那就回到了客户明确否掉的审批。
- **配阈值可以，配类型不行**：MVP 的 5 个类型是固定枚举，管理员只能改数值；要增类型走字典表迁移。理由同上——分类可以自由增删（那是给人用的），项目类型要参与统计（那是给数用的），两者不能一个待遇。

#### 6.6.6 报价单三个视图的显示差异（防止两种事故）

设计师提出的"预览默认隐藏成本"与 PRD 编辑态"实时显示毛利"看似冲突，实际是三个不同视图，需明确区分：

| 视图 | 成本列 | 毛利列 | 理由 |
|------|--------|--------|------|
| **编辑态** | 显示（`admin` 与 `member` 均可） | 显示 | 不显示就无法定价，这是工作必需 |
| **预览态**（发给客户前看效果 / 投屏 / 截图） | **默认隐藏**（可显式切换，每次进入默认关闭） | 默认隐藏 | 防"投屏给客户看时成本在屏幕上"，这是真实发生过的场景 |
| **导出·客户版** | **不出现**（服务端渲染时剥离） | 不出现 | 硬安全要求 |
| **导出·内部版** | 显示 | 显示 | 供老板复核。**仅 `admin` 可导出**，见下 |

**屏幕用"一格两行"，导出用"独立列"（v1.4 补）**

编辑器里 `reference_lowest_price` 不单独占一列（1366px 下 14 列会出横滚），而是并进供应商格做两行：`金桥桁架厂` / `最低 ¥25.00`，成本高于快照时转红显示 `高 ¥3.00`。这个处理是对的——"比最低贵 ¥3"这个结论离开供应商名本来就没意义。

**但导出必须给独立列。** 因为导出的 PDF/Excel 是平面载体，没有悬停、没有折叠，老板在纸上复核时看不到那第二行就等于没有这个信息。规则：
- **内部版导出**：必须有独立的「参考最低价」与「高于最低价」两列
- **客户版导出**：绝不出现（这属于内部成本信息，与成本同等级别处理）

> 一般原则：**屏幕上的折叠/悬停合并，不能自动继承到导出。** 导出是无交互平面，所有被折叠的信息要么展开成列，要么明确放弃。

**权限区分（`member` 能看但不能带走）**：`member` 可以在屏幕上查看成本与毛利（否则无法报价），但**不得导出含成本的内部版文件**。

> 理由：**屏幕可见是即时行为，导出文件是可转发资产，风险量级不同。** `member` 能算毛利，不代表应该能产出一个可以转发给客户的含成本文件。这条不做的话，"成本不泄露"就只防住了导出客户版，没防住内部版被误发。
>
> 若实际工作中 `member` 确实需要把内部版发给老板复核，MVP 的处理是：老板自己（`admin`）导出即可。若这条在实际使用中成为高频阻碍，P1 再加"指定成员可导出内部版"的授权开关。

**导出安全要求（必须由服务端保证）**：
- 客户版 PDF / Excel **由服务端渲染时剔除成本字段**，不得依赖前端隐藏列或 CSS。
- 客户版必须使用**独立的 DTO**，不得复用内部 DTO 再加 `hideCost` 之类的开关参数 —— flag 是最容易漏的一条路。
- 客户版 Excel 可保留「单价 × 数量 = 金额」的计算公式（客户改数量能自动算），但**不得含任何成本单元格、加价率单元格、命名区域或隐藏列**。导出前需自检断言：客户版文件中成本相关字段出现次数必须为 0，不为 0 则拒绝导出并告警。

#### 6.6.7 报价单状态机（只有三态，不加审批态）

`draft`（草稿，可反复改）→ `issued`（已发出，锁定快照，不可再改，只能复制重报）→ `void`（作废）

**明确不设 `已成交` 状态**：成交属项目/CRM 范畴，已在 Out-of-Scope。

**明确不做审批态（客户 Q5 口径，v1.8 定稿，不再讨论）。** 客户原话：「不要审批，不要发出蠢单就行。」

这句话值得原样留档，因为它把两条完全不同的需求区分开了：

> **客户要的是"不发出蠢单"，不是"我要当审批节点"。**
> 前者的解法是**系统拦截**（自检 + 通知），后者的解法是**人等待**（审批流）。
> 两者的成本差一个数量级，而前者对客户真实痛点的覆盖更完整 —— 老板不在的时候，审批流会让所有单停住，自检不会。

所以：**不加 `pending_review`、不加任何"不批准不能发"的节点。** 若将来有人提这个需求，先问一句"你是怕发错单，还是想每单都看一眼"—— 前者我们已经做了，后者才是审批。

**关于"老板想看一眼再发客户"**：不用审批流解决，用两个轻量机制替代（详见 8.1 第 14 项）：

1. **发送前自检（共 8 条，只有 1 条是阻断项）**：点「生成报价单」时跑一遍，命中则弹清单。

| # | 检查项 | 级别 |
|---|--------|------|
| 1 | 客户名或活动名为空 | **blocker**（唯一一项） |
| 2 | 整单毛利率低于**本单项目类型对应的阈值**（类型为空时用全局默认 25%，优先级见 6.6.5） | warning |
| 3 | 存在成本为手填的行（该行无有效价） | warning |
| 4 | 存在成本单价高于该主体**同性质 + 同税口径 + 同计价方式**下的当前最低有效价的行（没选最优供应商） | warning |
| 5 | 本单使用了软陈旧价格（超阈值未核价） | warning |
| 6 | 存在亏损行（`line_profit < 0`） | warning |
| 7 | 存在零价行（对客单价或成本为 0） | warning |
| 8 | 所用价格将在活动日期前失效（`effective_to` 早于 `event_date`） | warning |

**只有第 1 条阻断，且仅在 `issued` 时阻断，存草稿不阻断。**

为什么只有 1 条阻断：**一旦把 warning 做成阻断，用户会学会闭眼点"仍然继续"，然后所有提醒一起失效** —— 这和我把"毛利率低于阈值"从红改成琥珀是同一条逻辑。提醒的价值取决于它有多罕见。

（v1.3 修正）我先前在验收用例 TC-8.5 里把"客户名为空"也定成不阻断、允许代填「待补」。**这个判断我改掉**：报价单是对外文件，没有客户名就不是一份可发出的文件，而"待补"会变成永久垃圾数据。客户名为空在 `issue` 时阻断是对的。

**（v1.8 措辞修正）** 这一节的标题"只有三态"比它的目的更硬，架构师提醒得对。**目的是"流程简单到没人需要绕过审批"**，三态是实现这个目的的手段。将来若要做成交率统计（P2），加一个**不阻断流转**的统计态不违反本节；**不许加的是会卡住流转的状态机节点**（如 `pending_review` 不批准不能发）。按目的读这一节，不要按字数读。
2. **生成后通知**：报价单 `issued` 后向管理员发送一条站内通知（含单号、客户、金额、毛利率）。管理员看到不对劲自己去追，不需要当审批节点。

如果客户**明确要求阻断式审批**（不批准不能发客户），再于 P1 增加 `pending_review` 状态，届时需同步修改：状态机、工作台"待处理"统计口径、报价单台账筛选器、导出按钮的可用条件。**当前不预留，避免过度设计。**

#### 6.6.8 成本价取哪个值（R3 决议：两个值都记）

出单时成本默认取「该主体 + 该交易性质 + 同口径可比范围内的**当前最低有效价**」，并允许逐行手动换供应商。**同时落两个快照值**：

| 字段 | 含义 | 为什么必须存 |
|------|------|--------------|
| `cost_unit_price` + `supplier_id` | 实际采用的那家 | 算毛利 |
| `reference_lowest_price` | 录单时那一刻的最低有效价 | 三个月后最低价变了，没有这个值就无法回答"当时为什么没选最便宜的" |

这笔账很清楚：**多两列，换来"为什么这单贵了"这个问题的唯一答案来源。** 不存的话，自检第 3 条（成本高于最低价）会在发出后变成一笔无法追溯的糊涂账。

**阻断与放行的边界（关键，直接影响新库能否上线）**：

| 情形 | 表现 | 是否阻断出单 |
|------|------|--------------|
| 命中有效价 | 自动带入，`cost_source = price_book` | 不阻断 |
| 该主体无任何价 | 红色「无有效价」+ 出现「手填成本」输入框，此时「生成报价单」置灰 | **阻断，但填了成本即放行** |
| 全部价格已硬失效 | 同上，并显示灰色旧价「原价 ¥3,200（已失效）」作为参考占位符 | **阻断，但填了成本即放行** |
| 用了软陈旧价 | 琥珀提示「(!) 187 天未核价」 | 不阻断，允许出单，内部版导出留痕 |
| 手填成本 | 灰标「手填」，`cost_source = manual` | 不阻断 |

> **红线：阻断只能是"未填成本时阻断"，成本一填就必须能出单。** 否则新库第一天大量主体还没价（这是必然的），用户会发现系统根本出不了单，然后回 Excel —— 产品在第一天就死了。这是本节最重要的一句话。

**缺价行的对客价保持原值，不清零（v1.7 补）**

某行成本变缺（无有效价、或切换税口径后查不到）时，它的**对客价保持用户已经定过的值**，只有成本变红提示、`cost_source` 转 `manual`。

理由：对客价是商务判断，已经跟客户谈过或至少已经想清楚；成本缺失是数据问题。**用数据问题去清掉商务判断，会让用户在改口径/补价的瞬间丢掉已定的售价，而他自己可能没注意。**

这条也决定了切换税口径提示里那个"整单合计"该怎么算：缺价行仍计入合计，否则提示里给出的新合计与实际发出的单不一致 —— 而这正好又是 6.6.9.1 说的那类"看起来对、实际错"的东西。

**成本侧不能置空，要用标记表达（v1.9.1 补，架构师补完我没说全的另一半）**

我只说了对客价保持原值，漏了成本侧。正确做法：**`cost_unit_price` 保留旧口径的值**，同时 `price_missing = true`、`cost_source = 'manual'`、`price_id = NULL`。

不能置 NULL 的理由不是洁癖：`quote_items` 的金额列是 `NOT NULL` 无默认值，这是快照不可污染的前提。而**"缺价"的准确含义不是"这行没内容"，而是"这个数不再有价格库支撑、必须有人复核"** —— 用标记表达，不用 NULL 表达。放成 NULL 的代价是整个快照体系。

> **一条可复用的判断**：给一个字段留空和给它一个标记，区别在于"以后有没有人能查出这件事发生过"。空值是不可查询的，标记是可查询的。**凡是"事后要被人复核"的状态，都必须有名字。**

架构师把这条做成了**结构保证而非纪律**：`price_missing` 是生成列（由 `cost_source` 与 `price_id` 派生），切口径只需维护两个源字段，**不存在"忘了改第三个"**。方向上我认可 —— 凡是"靠人记得改"的规则，最终都会漏一次。

**手填成本的刻意不方便（采纳设计的方案，并补一条出路）**：手填框占位符显示灰色失效旧价，但**不提供一键采用**，必须自己敲。目的明确：不让过期价被静默使用。

但纯手敲会带来反效果 —— 用户嫌烦，干脆整个单子回 Excel 出。所以补一条显式出路：旁边给一个「按旧价重新录价」按钮，点了之后系统**自动创建一条 `effective_from = 今天` 的新 PriceBook**（复用 6.2 的版本化逻辑，旧价自动 superseded），然后本行直接采用新价格。

这是个关键区别：**不是"静默用旧价"，而是"显式确认这仍是当前价，并把它变成一条新价格记录"**。用户的动作只多一次点击，但价格库因此被修正了 —— 它把一次报价动作转化成一次录价动作，正好解决"没人愿意维护价格库"这个根本问题。

#### 6.6.9 含税口径怎么给客户（R4 决议：单口径 + 声明行，不做双口径导出）

**MVP 不做含税/不含税双口径导出。** 理由：双口径必须有 `tax_rate`，而 MVP 不采集税率（6.6.3），做了也只能算出错的数。**一个会算错的开关，比没有开关更糟** —— 用户点了之后会以为数字是对的。

替代方案（零计算成本，解决 80% 的沟通问题）：**在报价单上加一行口径声明**，由管理员在设置里选默认，出单时可改：
- 「以上报价为含税价，税率另计」
- 「以上报价为不含税价，税额另计」

这一行比两栏对照表更符合实际沟通场景 —— 客户问"含税多少"，业务员看一行字就知道怎么答，不需要系统算两遍。

**默认值已由客户定（Q7，v1.8 定稿）：报含税价。**

| 项 | 值 |
|---|---|
| `app_settings.tax_statement_default` | `'inclusive'`（显示为「含税」）—— **枚举值与全项目 `tax_basis` 值域一致**（`inclusive` / `exclusive`，见 OD-01），不要另起 `'含税'` 这种字面量 |
| 默认声明文案 | 「以上报价为含税价，税率另计」 |
| **成本取价口径** | **默认跟随本单声明（即默认取含税价）**，用户可在单上改 |
| 改口径时 | 按 6.6.9.2 给出**切换前后整单合计**，并区分自动定价行/手工定价行 |

**"成本取价口径默认跟随本单声明"这一句要单独记住，它是最容易实现错的一处。** 如果对客报含税、成本却默认取不含税价，毛利会被算高：客户付 113，你以为成本 100，实际要票成本 113 —— **整单毛利率凭空多出一截，而且每一行都对、每一项都合理，只有最后一行的结论是错的**（6.6.9.1 那类错误）。

所以两个口径**不是两个独立设置项，是一个选择的两面**：本单声明默认含税 → 取价默认含税。用户可以改，但**改一处必须同时改另一处**，不能各自为政。

**何时升级**：客户确认常用税率档（小规模 3%/1%、一般纳税人 13%/6%）后，P1 加 `tax_rate`，届时是"导出模板加一列"，不是重构。设计可以留口子，但**不要现在就把开关做出来**。

#### 6.6.9.1 为什么这个错误特别危险（记录一条通用判断）

设计团队把口径声明做成页脚注释时，自评了一句很准的话：

> **做成装饰文字不会报错。用户以为报的是含税，成本按不含税取，整单毛利算高、报出去亏钱——系统全程绿灯，数字还很漂亮。所有错误里这一种最难被发现，因为它看起来像"今天运气不错"。**

这条值得记成一条通用判断，因为它适用于本产品所有地方：

> **会报错的错误是安全的，不报错的错误才是危险的。**
> 凡是"两个值都合法、都能算出一个数、但其中一个是错的"的地方，系统必须强制二选一或显式确认，**绝不允许静默使用默认值**。

本产品里符合这条判据的地方：含税口径（6.6.9）、交易性质（6.6.1）、计价方式（6.6.1）、折算系数（6.6.2）、成本来源 `cost_source`（6.6.8）。这五处都不能"取个默认值先算着"。

**这条判据怎么用：不是"有 DEFAULT 就删"（v1.9.1 补，架构师把它做成可执行的）**

我原来只给了判据，没说边界。架构师按它扫了 46 个 schema + 53 个 path，先纠了这个用法上的坑，纠得对：**DEFAULT 分三类，只有第一类违规。**

| 类型 | 例子 | 判定 |
|---|---|---|
| **断言型**：替用户断言了一个业务事实，而另一个值同样合法 | `prices.tax_included DEFAULT true`、`prices.pricing_nature DEFAULT 'purchase'`、`quote_items.cost_source DEFAULT 'price_book'`、`quotes.tax_statement DEFAULT 'inclusive'` | **违规，必须删**。删掉之后用户必须显式选，选错了至少是他选的 |
| **计量型**：不存在"另一个合法值" | `version DEFAULT 1`、`sort_order DEFAULT 0`、`status DEFAULT 'draft'` | 合规 |
| **占位型**：必然被后续计算覆盖，且覆盖前不参与任何结论 | `total_cost DEFAULT 0`（recalc 必写）、`created_at now()` | 合规 |

**这个分类值得记住，因为它防止判据被用过头。** 一条判据如果不能说出"什么时候不适用"，它就会在下一次评审里被当成万能理由，然后被合理反驳一次，最后整条作废。**判据的边界和判据本身一样重要。**

架构师配套加了两条 lint，把判据变成构建失败而不是评审意见 —— 这比写在文档里更有效：`server/pricing/**` 与 `server/quotes/**` 禁 `COALESCE(x,1)` / `?? 'purchase'` / `|| 0` 兜底金额、口径、单位、性质；`sale_unit_price` / `cost_unit_price` 只允许报价计算模块与用户显式改价写入。**能写进 lint 的规则才是规则，其余的只能算倡议。**

#### 6.6.9.2 切换口径的提示必须给出"切换后的整单合计"

**关于提示文案，我和设计团队有一处分歧，以此处为准。**

设计团队的方案是：只提示"成本会变"，不提示"金额会变"，理由是"对客价由毛利率算，所以未必变；说金额会变会吓到人"。

**这个理由的前提不成立。** 按 6.6.5 / 6.6.8，对客价对**自动定价行**是 `成本 ÷ (1 − 毛利率)` —— **成本变了，对客价必然跟着变，整单合计也必然跟着变。** 只有手工改过对客价的行才不跟着变。

所以"金额不变"这个说法在多数情况下是**错的**，而后果与 6.6.9.1 描述的是同一类事故：用户以为只是换了个口径标签，实际手里这张单的总额已经变了，然后发给客户。

**规则：切换提示必须给出切换前后的整单合计对比，并区分两类行。**

```
换成「不含税」后，系统会重新查每一行的成本价：
- 3 行成本会变（其中 2 行自动定价，对客价跟着变；1 行手工定价，只有毛利变）
- 另有 1 行只有含税价，切过去会变成缺价
整单合计：¥12,000 → ¥11,300
```

三个必须项：
1. **给出切换前后的整单合计**。这是用户唯一真正关心的数字，也是"静默变额"最容易造成事故的地方。没有这个数字的确认框只是免责声明，不是提示。
2. **区分自动定价行与手工定价行**，因为它们的后果不同（前者改金额，后者只改毛利）。
3. **预告会变缺价的行**（某行只有另一口径的价）。否则用户切完看到红色会以为系统出错。

**保留设计团队的两条好判断**（这两条我认同并采纳）：
- **N = 0 时（没有行受影响）不弹窗**，切换后只留一行轻提示「已切换，这单没有受影响的成本行」。没行受影响还弹窗就是纯噪音，而噪音会让真提示失效。
- **提示里举一个真实价差**（如「金桥桁架厂 含税 ¥3,200 / 不含税 ¥2,900」），比抽象描述更快让人判断这次切换值不值。

**试算必须零副作用（v1.9.1 补，架构师落地后回填）**

"切换前的整单合计"要算出来，只能靠试算接口（`POST /quotes/:id/tax-basis/preview`）。三条硬要求：

1. **不落库、不改 `last_used_at`、不写价格变更日志、不触发通知。**
2. **不允许"先写了再回滚"** —— 回滚仍然持行锁、仍然触发触发器，在并发下不是零副作用，是"副作用被撤销过"，两者不等价。
3. **算术只有一份**：试算与 `issue`、`recalculate` 必须调**同一个**汇总函数。否则"共用逻辑"只是口头共用，某天有人只改了一处，**提示给客户的新合计与实际发出的单就会分叉** —— 而这条分叉恰好出现在"用户最依赖这个数字做决定"的时刻。

> 这条同样是 6.6.9.1 判据的应用：**两个地方各算一遍，本身就是一个"不报错的错误"**。它不会崩，只会在某个版本之后给出两个都对不上对方的数。

#### 6.6.10 附件的三条边界（v1.8 新增）

「图片与链接附件」是用户勾选的 P0 之一。但评审到五轮时我发现一件事：**它一条验收用例都没有**。前面 155 条 TC 全在价格口径上，附件的上传、白名单、外链、导出全没人管。而附件的失败模式和价格口径不同 —— 它不产生"错数"，它产生的是**图裂、打不开、和不该给客户看的东西给出去了**，都是事后才发现的类型。

三条边界：

**① 客户版只带物料图，不带"价格附件"**

附件挂在两个地方：`PricedItem`（物料参考图、淘宝链接）和 `PriceBook`（供应商报价截图、对方的微信截图）。前者是对客材料（"客户想知道这块背景板长什么样"），后者是**底账证据**（"这家报了 3200"）。

客户版导出**只带 `PricedItem` 的图片**，`PriceBook` 的附件一律不出。理由与 TC-12.x 剥离成本是同一条：报价截图里几乎必然带着供应商名和价格，一张图漏出去等于把成本表发给客户。

**② 附件不做物理删除**

报价单明细是全量快照（决策 C），但快照里存的是附件的 `url`，不是文件本体。如果删物料/删价格时把文件物理删掉，**历史报价单会图裂** —— 而且是几个月后打开旧单才发现。

规则：删主体/价格只解绑或软删附件记录，**文件本体保留**；存储清理只能由"无任何记录引用且超过 N 天"的离线任务做，且该任务必须能列出待删清单供人核对。

**③ 外链只存不抓，渲染必须当作不可信输入**

淘宝外链、供应商网址是用户手填的。系统**不抓取、不转存、不预览**（抓取会引入 SSRF 和一堆超时问题，收益只是省一次点击）。

渲染时三条硬要求：
- 只接受 `http(s)` 协议，`javascript:` / `data:` 一律拒
- 新窗口打开 + `rel="noopener noreferrer"`
- 用户填的 URL **不得**出现在任何会被当作代码/样式执行的位置

同理，`SVG` 不列入图片白名单 —— SVG 可以内嵌脚本，同源打开就是 XSS。白名单保持 `jpg/png/webp/pdf`。

### 6.7 权限设计（Q8 定案：分层开放）

**客户 2026-11-04 选定方案 (c) 分层开放。** 三个选项的完整对比留档如下，避免将来有人以为这是我们的偏好：

| 选项 | 做法 | 代价 | 结论 |
|---|---|---|---|
| (a) 维持现状 | 录价仅 `admin`。接受"价格库维护是老板一个人的事" | 价格库增长受限于老板一个人的时间；`manual_cost_line_ratio` 目标需作废或改为随录价次数考核 | 否 |
| (b) 半开放 + 待复核 | `member` 可录但标 `pending_verify`，`admin` 一键复核 | 多一个价格生命周期状态，牵连比价/出单可用性定义；若 pending 价可参与出单，复核只是事后追认 | 否 |
| **(c) 分层开放** | `member` 可**新建**价格；`admin` 额外可**覆盖/停用**已有价 | 与用户原话"管理员可改价"偏差最小，且改造了最需要改造的那一段 | **客户选定** |

**权限矩阵（v1.9，按 (c) 落地）**

| 能力 | `admin` | `member` |
|---|---|---|
| 查看价格、比价、历史趋势 | 是 | 是 |
| **新建价格**（`POST /prices`） | 是 | **是** |
| **覆盖 / 停用已有价格**（`PATCH /prices/:id`、archive） | 是 | **否** |
| **改折算系数 `base_unit_qty`、改交易性质 `pricing_nature`** | 是 | **否**（属覆盖，不是新增） |
| **`refresh-prices`（批量改写草稿成本）** | 是 | **否** |
| **删物料 / 删人员 / 删供应商** | 是 | **否** |
| 改分类、改设置、管账号 | 是 | 否 |
| 新建报价单、出单 | 是 | 是 |
| 屏幕查看成本与毛利 | 是 | 是 |
| 导出客户版（无成本） | 是 | 是 |
| 导出内部版（含成本） | 是 | **否** |

**判定必须收敛在两处，且不许合并成一个函数**

```ts
// src/domain/permissions.ts —— 唯一判定点
canCreatePrice(role)                 // member: true   admin: true
canOverridePrice(role)               // member: false  admin: true
```

**禁止合并成 `canEditPrice`。** 这不是命名洁癖：合并之后，"新建"和"覆盖"的风险差别会被抹平，而它们几乎是相反的 —— 新增一条价最坏是多一条可疑记录（可查、可删、可被版本覆盖）；覆盖一条价最坏是**悄悄改掉了全公司正在用的成本**。**一个函数名下两种风险，迟早有人按低风险那个实现。**

[硬约束] 禁止在 route / service / 组件里写 `role === 'admin'`。Q8 从 (a) 改到 (c) 只用了改两行，将来改回去也必须是两行。

**为什么"允许成员录价"在风险上反而更低（留档，权限设计依据）**

> 手填成本是"一个没有记录、无法追溯、无法纠正的错数"；录进库的错价至少"有记录、有署名、可被下一条版本覆盖"。**在成员已经能手填的前提下，禁止他录价，在风险上反而是更差的那个选择。**

这段话也解释了为什么用户原话"管理员可改价"没有错、我们却要分层：用户说的"改价"指的是**覆盖已有价格**，而"录一条新供应商的价"是另一件事。把两者打包成一个权限，是我们在实现时做的合并，不是用户的要求。

**两条无论选哪个都必须成立的配套**（已落地）：每条价格显示录入人/最后修改人；管理员工作台有「成员最近改价」可见清单（**不阻断、只可见**）。

## 7. 关键业务流程

### 7.1 录价流程（物料 / 人员同构）

```
登录（role = admin 才能进录价）
  → 选择分类（物料树 / 人员树）
  → 搜索是否已存在该主体
      ├─ 有 → 打开详情，点「新增报价」
      └─ 无 → 新建主体（名称 + 单位 + [人员额外：计价方式 / 是否含差旅] + 规格）
  → 选择供应商（可选已有 / 新建供应商，填类型：线上/定做/租赁/兼职/自有）
  → 填价格：单价 + 单位 + 含税标记 + 最小起订量
  → [可选] 加数量阶梯：min_qty / max_qty / unit_price，可加多档
  → 填生效期：effective_from（必填）/ effective_to（可空 = 长期）
  → [可选] 传参考图 / 贴淘宝等外链
  → [可选] 填报价来源备注（"2026-10 老王微信问价"）
  → 保存
      ├─ 系统校验：
      │   ① 该主体 + 该供应商 是否存在生效期重叠的旧价格？
      │        ├─ 无重叠 → 直接创建
      │        └─ 有重叠 → 弹出「将结束旧价（失效日 = 新价生效日 - 1 天）」，用户确认后旧价置为 superseded
      │   ② 阶梯是否连续无重叠？是否有档位单价高于低档（违反常识）？→ 警告但不阻断
      └─ 完成，价格立即进入比价与出单可用池
```

**设计要点**：录价表单默认只露 4 个必填（供应商、单价、生效日、单位），阶梯/附件/备注全部折叠为「展开更多」。录价路径每多一个必填，录价意愿就掉一截——这是这套系统的生死线。

**批量录多家的路径（采纳设计的「保存并再录一家」）**：采购问一次价通常拿到 3-5 家报价。保存成功后不关闭录入面板，而是：
- **保留**：主体（物料/人员）、生效日（同一批询价通常同一天生效）、交易性质
- **清空**：供应商、单价、单位（**必须清空**，因为不同供应商的报价单位经常不同，淘宝按张、厂按㎡）、阶梯、起订量、附件、来源备注
- **焦点回到**供应商搜索框，并给一条轻提示「已存 金桥桁架厂 · 还能再录几家」

这把"录 5 家价"从 5 次开合降为 1 次，是提高「录价转化漏斗」最直接的一刀（该漏斗是 12 节里的第一指标）。

### 7.2 比价流程

```
搜索框输入（名称 / 别名 / 分类树点击）
  → 命中 PricedItem 列表（显示分类、单位、当前最低价）
  → 进比价页（单个主体的横向对比）
      → 顶部：数量档切换器（如 100 / 300 / 500，或自定义 qty）
      → 主体信息：名称、规格、参考图、淘宝链接、单位、比价基准单位
      → **先按交易性质分段（Tab 切换）**：买断 / 租赁·按天 / 定制加工。同一物料同时存在多组时才有 Tab，只有一组时不显示
      → **摘要条（44px，本页最重要的落点）**：只针对**当前选中的交易性质组**，一句话回答"我该找线上还是找线下"
            例：`最便宜 ¥28.00 金桥桁架厂（线下定做厂）｜次低 ¥32.00 喷绘之家（线上电商）｜同口径可比 4 家`
                `线上最低 ¥32.00，线下最低 ¥28.00（线下便宜 12.5%）`
      → 供应商横向列表（按该 qty 命中的阶梯价升序）
            ├─ 每张卡片：供应商名 + 类型标签（线上/定做/租赁/兼职/自有）+ 该档单价 + 单位 + 含税标记 + 起订量 + 生效期 + 交期
            ├─ 单位不一致时显示折算价「折算 60 元/㎡（原 5 元/张）」；未填折算系数则琥珀「未折算，不能比」且不参与最低价
            ├─ 最低价卡片高亮标注；并列最低两家并列标注
            └─ 卡片可展开：该供应商此主体的历史价格小趋势图 + 软陈旧标记「(!) 187 天未核价」
      → 底部：一键加入报价单（带主体 + 选定供应商 + 数量）
```

**设计要点**：比价页是这个产品最值钱的一屏，信息密度可以高，但**摘要条必须是视觉第一落点**。它回答的不是"多少钱"，而是**"我该找线上还是找线下"** —— 这正是用户"同一个物料线上淘宝和线下定做厂价格差很大"这个困惑的答案。

**摘要条的硬约束：不能跨交易性质混算。** 如果一个物料同时有买断价和租赁价，摘要条只能说当前 Tab 这一组的结论。否则又会回到 6.6.1 那个"按租价报买断活动"的事故。这也是为什么 Tab 要在摘要条之上。

### 7.3 出报价单流程

```
新建报价单 → 填客户名 / 活动名 / 活动日期
  → 循环：搜索并勾选物料 / 人员
        → 每勾一项，填数量
        → 系统按「今天 + 数量」解析当前有效 PriceBook 与阶梯档
              ├─ 命中 → 取 unit_price 作为 cost_unit_price，自动带入
              └─ 未命中（无有效价/全部过期）→ 红色提示「该主体无有效价格」，要求手填成本并标红标记
        → 默认采用最低有效价供应商；用户可下拉换供应商（成本随之变）
        → 系统按 target_margin_rate 自动算 sale_unit_price（如毛利 40% → 售价 = 成本 / 0.6）
        → 用户可直接改 sale_unit_price（改后该行毛利率单独显示，不再跟随整单率）
        → 实时更新行毛利 + 整单毛利 + 整单毛利率
  → 排序 / 加说明 / 标记哪一行不在客户版显示
  → 保存草稿（可反复改，编辑态**显示**成本与毛利，否则无法定价）
  → 点「生成报价单」
        → **发送前自检**（不阻断，命中任一条弹确认清单，用户确认即可继续）：
        │    ① 整单毛利率 < 阈值（默认 25%，可配）
        │    ② 存在成本为手填的行（该行无有效价）
        │    ③ 存在成本单价高于该主体当前最低有效价的行（没选最优供应商）
        │    ④ 客户名或活动名为空
        │    ⑤ 本单使用了软陈旧价格（> 90 天未核价）
        → 状态置 issued，写入全部 *_snapshot，此后活数据变动不影响本单
        → 向管理员发一条站内通知（单号 / 客户 / 金额 / 毛利率）—— 替代审批流
        → 预览态：成本与毛利**默认隐藏**（防投屏/截图时露成本），可显式切换
        → 导出两个明确命名的按钮：
             客户版 PDF/Excel（服务端渲染时剥离成本字段；Excel 保留"单价×数量"公式但不含成本单元格）
             内部版（含成本与毛利，供老板复核）
        → 归档进报价单台账（可按客户名 / 单号 / 活动名搜）
  → [后续] 客户要改版 → 点「复制重报」，version + 1
```

**评分口径**：Reach 1-10（季度内受影响用户/使用频次折算）；Impact 0.25/0.5/1/2/3；Confidence 50%/80%/100%；Effort 1-10（人月）。

### 8.1 P0 — 跑通「录价 → 比价 → 出报价单」闭环的最小集合

| # | 功能 | Reach | Impact | Conf | Effort | Score | 说明 |
|---|------|-------|--------|------|--------|-------|------|
| 1 | 账号登录 + 角色权限 + **成本价字段级隔离** | 10 | 3 | 100% | 2 | **15.00** | 成员能算毛利但导出不露成本 |

| 9 | **勾选生成报价单（自动匹配价 + 成本/毛利 + 快照）** | 9 | 3 | 95% | 6 | **4.28** | 产品心脏，Effort 最高 |

| 12 | **历史价格趋势（按主体×供应商的版本序列 + 涨跌）** | 7 | 2 | 80% | 3 | **3.73** | 用户已勾选必做，凭 Confidence 低分但仍必须做 |
| 13 | **图片与链接附件（物料参考图 + 淘宝外链）** | 8 | 1 | 100% | 2 | **4.00** | 用户已勾选必做，Effort 低 |

> 第 14 项是 P0 里 RICE 得分最高的一项，但它的本质是"一道确认清单 + 一条通知"，不是新模块。它的存在让"不做审批流"这个决定站得住——老板的安全感不必通过流程实现。

> 注：第 12、13 项 RICE 分数偏低，是因为 Impact/Confidence 的客观评估如此，但**用户已明确勾选为必做**，优先级不受分数影响。RICE 在这里的作用是帮助排开发顺序（先做分数高的），不是用来砍已确认范围。

**建议开发顺序（按 Score 降序）**：14 自检 → 1 权限 → 2 供应商 → 10 价格有效期 → 3 分类 → 11 阶梯价 → 4 人员库 → 6 比价页 → 5 物料库 → 7 导出 → 8 搜索 → 9 出单 → 13 附件 → 12 历史趋势。

> 这里有一个产品判断凌驾于 RICE 之上：**第 9 项「勾选生成报价单」必须在第 2 周就能跑出一个能点的粗版本**，哪怕丑、哪怕只有 3 个字段。因为整个产品的成功指标是"报价单从系统出"，如果到第 6 周才见到第一张能用的单子，团队会先退回 Excel 然后就再也不回来了。建议做法：先用硬编码假数据打通"勾选 → 算价 → 出 PDF"，再做真实价格库。

## 9. MVP 范围

**只做 14 项 P0，一条链跑通：**

> 管理员录物料价 / 人员价（多供应商、交易性质、阶梯、有效期、图片链接、可选折算系数）→ 任何人搜物料看一屏比价（按交易性质分组、自动标最低、看历史趋势）→ 勾选攒报价单（自动匹配有效价、实时算毛利）→ 发送前自检 → 导出客户版 PDF（服务端剥离成本）。

**明确的验收门槛**：一个没参与开发的人，能在不培训的情况下，用 20 分钟完成："录一个新物料在 2 家供应商的价格（含一档阶梯价）→ 出一张含 8 行的报价单 → 导出 PDF"。

## 10. Out-of-Scope 清单（每条带原因）

| 不做 | 原因 |
|------|------|
| **复杂项目成本核算**（多阶段预算、计划 vs 实际、费用归集） | 用户明确不做。这是 ERP 的核心模块，一旦引入就要连带动预算科目、期间、报销，MVP 会被拖垮 |
| **审批流（阻断式）** | 用户明确不做。且是**反向激励**：5-10 人公司改个价还要走审批，会直接杀死录价意愿，比不录价更糟。老板"想看一眼再发客户"的诉求用「发送前自检 + 出单通知」替代，详见 6.6.7 |
| **ERP / 财务系统集成、开票、合同管理** | 用户明确不做。属另一条业务链 |
| **供应商门户（让供应商自己登进来报价）** | 这是极效361/会展邦的模式。需要外部账号体系、消息通知、资质审核、对外安全隔离，工作量翻倍，且与"公司内部工具"定位直接冲突。我们要的是**自己记下别人报的价**，不是搭一个询价平台 |
| **库存管理 / 出入库 / 库存预警** | 活动物料大量是一次性定制、租赁、按㎡计价，**没有库存概念**。硬加会让录价表单变长，降低录价意愿（致命） |
| **客户 CRM / 线索 / 合同跟进** | 不在"录价→比价→出单"闭环内，属另一产品 |
| **人员排期 / 档期管理** | 这是「婚礼总动员」类产品的核心诉求，与"价格底账"是两个不同问题，混做会两头不讨好 |
| **报价单在线签署 / 电子合同** | 法务链路，MVP 出 PDF 即可，微信发文件是现有习惯 |
| **增值税额拆分（专票/普票）** | MVP 只记 `tax_included` 布尔标记，做税额拆分需要税率表和税务口径确认，收益低于成本 |
| **移动端 App / 小程序** | 用户明确"电脑网页为主"。但**不等于手机上什么都不给看**——见下方「移动端边界」的明确界定 |
| **移动端录入与出单** | 录价、出单是重表单与密集表格操作，压进 375px 只会做出两个都不能用的版本。同时也避免"随手在手机上改价"导致的价格失控 |
| **全局单位换算字典 / 单位换算图** | 换算系数是每个物料各自的规格事实（换克重就变），不是行业常量；且大量"1 套 = 一堆东西"客观无法换算。改用"价格条目上的选填折算系数"，成本低得多且不错，详见 6.6.2 |
| **税率采集与税额拆分** | MVP 只记含税/不含税布尔标记。跨税口径不标最低价（6.6.3）。加 `tax_rate` 需先向客户确认常用税率档，列 P1 |
| **报价单「已成交」状态** | 成交属项目/CRM 范畴，不在本次闭环 |
| **多币种 / 汇率** | 国内活动公司人民币结算为主 |
| **智能比价建议 / 自动涨价预警** | 需要足够历史数据才有意义，放 P2 之后 |
| **对外公开的产品目录 / 客户自助查价** | 与"内部系统"定位冲突，且涉及价格泄露风险。**移动端只读页也不得用免登录 token 实现**，见 10.1 |
| **含税/不含税双口径导出** | 需要 `tax_rate`，MVP 不采集（6.6.3）。用"口径声明行"替代，见 6.6.9 |

### 10.1 移动端边界（明确界定，不留模糊）

**客户 Q4 已答（v1.8 定稿）：手机不是刚需，「能看就行」。**

这条把移动端从"要投工期"降成"复用现有详情页做单列布局"。三条写死的结论：

1. **移动端只做只读**，不做录入、不做改价、不做独立工程。
2. **三档响应式**，见下表。
3. **不立项独立移动端**，R12 结案。

| 档位 | 布局 | 录入能力 |
|------|------|----------|
| **≥ 1024px** | 完整（表格 + 侧栏，主场景） | 可编辑 |
| **375px – 1023px** | **单列堆叠，只读三页**：报价单详情（含明细与金额）/ 物料或人员价格详情 / 比价结果。其余页显示「这个页面在电脑上打开」 | **只读**（不可录入、不可出单、不可改价） |
| **< 375px** | 提示"屏幕过小，建议用电脑打开"，仍可看报价单金额 | 只读 |

**关于"≥1024"与"只读"的关系，这里有一处必须写清的例外，否则会误伤：**

客户说的"375–1023 只读"是**手机和平板的实际场景**，不是一条宽度规则。技术上判定只读**用指针类型**（`pointer: coarse`），不是宽度 —— 因为桌面用户把浏览器窗口拖窄到 900px 时明明有鼠标键盘，按宽度一刀切会让他失去编辑能力，而这是每天都会发生的操作。

所以两句话各管一件事：
- **宽度管布局**（三档单列/完整）
- **指针管能力**（粗指针只读）

**这不违背客户口径，是把客户的口径落在一个不会误伤桌面用户的地方。** 真实设备上两者结果一致：手机和平板都是粗指针。此差异已记入 `OPEN-DECISIONS.md` 供 Phase 2 复核。

**判定规则（v1.4 修正）：以指针类型为主、宽度为辅**

`readonly = pointer: coarse`（触摸为主即为只读），宽度只决定布局，不决定权限。

我原先写的是"宽度 < 1024 → 只读"，这是**把设备能力当成了布局问题**。设计师指出会误伤桌面窄窗口用户，这个判断成立。修正后核心意图（手机上别做录入）完整保留：判的是"有没有鼠标键盘"，而不是"窗口有多宽"。

**两条必须同时成立的约束：**

1. **`pointer: coarse` 只做体验层降级，绝不能当权限边界。** CSS 媒体查询任何人都能伪造，改动它只需要开发者工具。**真正的权限在服务端的 `role`**（改价只有 `admin`）。这两件事不能混为一谈——否则会以为"手机上做不了录入"就等于安全。
2. **降级要给出原因，不能只是按钮消失。** 只读态需明确显示「手机上只能查看，改价请在电脑上操作」，与我反对"直接阻断"是同一条逻辑：**让人以为系统坏了，比让他换个设备更糟。**

**优先级：P0。** 这是"复用现有详情页 + 单列布局"，不是新建一套移动端，成本很低。**不缩减为"只做报价单一个页面"** —— 项目经理在现场查价（R12 场景）需要的是物料价格详情和比价结果，只给报价单等于没解决。

**安全硬约束：移动端只读页必须走登录态（如 `/q/:id`），禁止使用免登录 token 路由（如 `/q/:token/view`）。**
两个原因：
1. 免登录 token 链接一旦被转发，等于把客户名 + 报价金额泄露给任意第三方，且无法追溯。价格是这家公司最敏感的数据。
2. 它实质上是"客户自助查看报价单"功能，已在 Out-of-Scope（见上表"对外公开的产品目录 / 客户自助查价"）。**不做，就不要留这个口子**，否则上线后一定有人把链接发出去。

**为什么不做独立只读移动端（客户已答，R12 结案）**

我原先担心「项目经理在活动现场临时加项要查价」是高频刚需，因此把它挂在 R12 上等确认。客户的回答是**不是刚需**，理由也合情理：现场加项通常直接打电话问老板，不会去查历史价。

所以：**不立项、不加工期、不做独立工程**。只读三页复用现有详情页的数据与组件，只做单列布局。

**保留一条将来翻案的条件**（写给 Phase 2）：如果上线后出现"同一人在同一活动里用手机打开价格详情 ≥5 次"的行为数据，说明现场查价是真的，那时再立项 —— **用行为数据翻案，用不到口头需求**。

### 11.6 视觉方向决策记录（PM 拍板，供设计与后续复盘）

**决策：采纳设计师的「墨黑 + 纸白 + 朱砂」，不采用 enterprise 知识库建议的深蓝/藏青。**
即：`--ink` 墨黑主色、纸白底、朱砂作行动色、琥珀作风险色、绿作有效/正向色。

**为什么推翻我自己先前的建议**：我在给设计的信里引用了 `enterprise.md` 的"深蓝/藏青"作为基线，但那是 ERP 的行业惯例启发式，不是本项目的事实判断。设计师提了三条反驳，我认为成立：

1. **冷蓝底会削弱绿色的话语权。** 在这套系统里，绿承担的是最关键的判断（最低价、正毛利），而密集表格里冷蓝背景与绿同属冷区，会互相干扰辨识。墨黑是无彩中性，绿和琥珀各自都能跳出来。这是技术性理由，比"像不像 ERP"重要。
2. **朱砂本身就落在橙色系**，正好接替"橙色作行动色"的角色，让琥珀专心做风险提示，两个颜色不抢同一个语义槽。
3. **这套系统对外不展示**，所谓"品牌"实际只剩一件事：让报价员觉得这是我们公司自己的东西。墨黑 + 纸白 + 一处朱砂，对应的是报价单、报价章、红笔圈价这些报价员真实的工作物件，比"专业蓝"更有归属感。

**采纳这一条的前提约束（必须满足，否则复评）**：

- **朱砂与危险红必须在形态上永不同槽。** 朱砂只做**填充按钮 / 选中态 / 强调描边**；危险红只做**文字 / 图标 / 细描边 / 角标 / 提示条背景**。两者不得出现在同一形态层级。这是硬约束 —— 朱砂是红偏橙，与危险红同属红色家族，只靠色相区分在色觉障碍用户和小屏幕上都不可靠。
- **两者明度差建议 ≥ 18（L\*）**，并在设计稿里标注实际色值。若做不到，则朱砂必须从"红偏橙"往"朱偏褐"压一档，拉开与危险红的距离。
- 需交付一份对比度核查表，至少覆盖 5 组关键配对：墨黑文字/纸白底（正文 ≥ 4.5:1）、白字/朱砂底（按钮文字 ≥ 4.5:1）、朱砂文字/纸白底（若用于强调）、危险红文字/纸白底、琥珀文字/纸白底。
- **不得因采用墨黑而降低信息密度** —— 色彩是次要的，操作效率是主要的。墨黑方案不得导致为了"留白气质"而把表格行高放大、列数减少。

**v1.4 补充三条（来自设计的实测反馈）**

1. **朱砂字压在纸白上做不成 4.5:1，因此禁止朱砂做文字色。** 实测：白字在朱砂底 4.60:1（余量仅 0.10）、朱砂字在纸白底 4.33:1（不达标）。而朱砂既不能提亮（白字会跌破 4.5），也不能压深（与危险红的明度差 18.98 会跌破 18）。**这是一个三向约束的死角，不是没调好。** 结论：**链接与行内强调另用信息青（5.04:1），红族只保留两个角色——朱砂做填充、危险红做文字。** 这与我"朱砂只做填充"的原约束一致，此处只是把它确认为唯一可行解。
2. **朱砂按钮的悬停/按下态绝对不能降低对比度。** 白字在朱砂上只有 4.60:1、余量 0.10，**任何 5% 的白色叠加或提亮都会把它打到 4.5 以下**。要求：hover/active 用阴影、描边或压深处理，**禁止用变亮/加白**。这条不写清，前端做悬停态时的默认做法就是把按钮调亮。
3. **深色皮肤需要反转明度关系**（危险色要比行动色更亮），并单独核查一组对比度，不能沿用浅色的结论。

**这个决策不影响工期**（换色只动 token），但影响所有后续截图与宣传素材，所以记录在此以免反复。

## 12. 数据埋点方案

> MVP 必须埋点，否则上线后无法判断"这套系统到底有没有被用起来"。用户量只有 5-10 人，所以埋点目的是**诊断行为卡点**，不是做增长分析。

| 事件类别 | 事件名 | 触发时机 | 关键属性 | 要回答的问题 |
|----------|--------|----------|----------|--------------|
| 获客/登录 | `user_login` | 登录成功 | user_id, role | 每周有几个人真的在用 |
| 激活 | `price_created` | 成功保存一条价格 | item_type, supplier_type, has_tier, has_attachment, tier_count, filled_seconds | **录价表单是不是太长了**（看 filled_seconds 和 has_tier 比例） |
| 激活 | `item_created` | 新建物料/人员 | item_type, category_id | 库里在往哪个分类长 |
| 核心动作 | `compare_viewed` | 打开比价页 | item_id, supplier_count | 比价页是不是真被当入口用 |
| 核心动作 | `compare_qty_switched` | 切换数量档 | item_id, qty | 阶梯价有没有人真的在用（关键验证） |
| 核心动作 | `compare_cross_unit_seen` | 比价页出现"未折算不能比"的行 | item_id, unresolved_count | **折算系数缺口有多大**——直接决定要不要向客户追讨更多换算关系 |
| 核心动作 | `price_trend_viewed` | 打开历史趋势 | item_id, supplier_id | 趋势功能是否有价值 |
| **转化（最重要）** | `quotation_created` | 新建报价单 | user_id | 出单是否在系统里发生 |
| **转化** | `quotation_issued` | 报价单状态转 issued | quotation_id, line_count, total_cost, total_price, margin_rate, has_overdue_price, has_stale_price, selfcheck_hits | **闭环是否跑通；有没有用到过期/陈旧价（关键质量指标）；自检拦了几次** |
| 转化 | `quotation_exported` | 导出客户端版/内部版 | quotation_id, export_type | 客户版 vs 内部版的使用比例 |
| 留存 | `session_start` / `session_duration` | 会话开始/结束 | user_id | 单次使用时长（< 2 分钟 = 只查了一下） |
| 异常 | `price_match_failed` | 出单时某行找不到有效价 | item_id, reason(**no_price** / **all_expired** / **found_but_not_used**) | **拆清"真缺价"与"有价没用"——两者要修的东西完全相反，详见 12.1.1** |
| 异常 | `quotation_abandoned` | 草稿超过 24h 未 issued | quotation_id, last_line_count | 出单流程在哪一步卡住 |
| 异常 | `error_occurred` | 前端异常 / API 5xx | error_type, page | 技术质量 |

**实现要求**
- 事件命名 `{对象}_{动作}`；属性统一带 `user_id`、`timestamp`、`device`、`app_version`。
- 不采集任何客户名称、活动名称、供应商联系方式的原始内容——只上传 ID 和数值属性。
- 每日聚合产出「录价转化漏斗」：打开录价页 → 开始填写 → 保存成功，**逐级流失率是判断这套系统能不能活的第一指标**。

### 12.1 两个质量指标的口径（必须精确，否则监控会做歪）

这两个指标最容易理解错。定义如下，架构师按此实现：

| 指标 | 公式 | 目标 | 说明 |
|------|------|------|------|
| `has_overdue_price` | 本单是否存在 `cost_source = price_book` 且该 PriceBook 为**硬失效**（`effective_to < 出单日`）的行 | **= 0**（硬性红线） | 衡量"脏数据有没有流到客户报价单"。理论上不该发生，一旦 > 0 说明价格匹配逻辑有 bug 或有人绕过校验 |
| `manual_cost_line_ratio` | `cost_source = manual` 的行数 / 总行数 | 4 周 < 30%，3 个月 < 10% | **衡量"价格库有没有被真正用起来"的体温计** |

**`has_overdue_price` 的统计口径：手填成本不计入。**
理由：手填成本不是脏数据，它是新库阶段的**正常且必要的兜底**。如果把手填算进这个指标，上线首月必然是 100%，指标当场失去监控价值 —— 而**一个首月就爆表的监控指标，团队会永久性忽略它**，连带把真正的过期价事故一起忽略。

手填本身当然也要被盯，但它盯的是"库够不够用"，不是"数据对不对"，所以单独用 `manual_cost_line_ratio` 表达，两者不要混。

> 补充：`manual_cost_line_ratio` 与 13.2 的「报价单价格复用率」互为补数（复用率 ≈ 1 − 手填率），实现时只算一个，展示时可两个口径都显示，但**不要定义成两个独立采集的事件**，避免数字打架。

#### 12.1.1 手填成本必须拆成两种原因（v1.6 补，设计团队指出的结构性问题）

`manual_cost_line_ratio` 单独一个数**无法指导行动**，因为"手填"背后有两条完全不同的因果链，需要完全相反的对策：

| 原因 | 含义 | 该修什么 | 埋点 reason 值 |
|------|------|----------|----------------|
| **真缺价** | 这个主体在这个供应商下根本没有有效价 | 覆盖率问题：录价权限、录价速度、冷启动导入 | `no_price` / `all_expired` |
| **有价没用** | 库里有可用价，但用户仍然手填了 | **体验问题**：搜不到、搜索词不对、不会勾选、不知道有比价 | `found_but_not_used` |
| **另一口径没价**（v1.9.1 补） | 切换税口径后，某行只有另一口径的价，切过去就变缺价 | **补录问题**：让供应商补另一口径的报价 | `basis_switch_missing` |

**为什么必须拆**：如果只有一个数，团队会默认"是体验问题，去优化录价表单"——而如果是权限问题，优化表单毫无用处。反之亦然。**一个不能指向对症动作的指标，等于没有指标。**

现有埋点里的 `price_match_failed` 已经记录了 `no_price` / `all_expired`，**必须补 `found_but_not_used` 这一支**：当用户在某行存在可用有效价的情况下仍然进入手填，单独上报。

**目标值的正确解读（v1.6 提出，v1.9 解除限制）**：
- 「手填率 < 30%」只有在**录价权限覆盖到实际拿价的人**这个前提下才成立。若录价仅管理员可用，这个目标从结构上不可达 —— **不可达的 KPI 比没有 KPI 更糟，因为团队会去追一个幻影**。
- **Q8 已定为 (c) 分层开放（6.7），成员可新建价格，该前提成立，`manual_cost_line_ratio` 恢复为可考核指标。**
- 但**不建议上线首月就拿它考核**：冷启动期价格库本来就不全，第一个月的高手填率是"还没录"而不是"没人用"。**第 2 个月起用它考核，第 1 个月只用来看趋势。**
- 同时盯一个新的、与权限无关的指标：**`found_but_not_used` 占手填总量的比例**。这个数与权限无关，纯粹反映产品好不好用 —— **它是"体验是否达标"的诚实指标**，目标 < 20%。

## 13. 成功指标

### 13.1 上线后 4 周的验收线

| 指标 | 目标 | 不达标说明什么 |
|------|------|----------------|
| 有效价格条目数 | ≥ 150 条（覆盖 ≥ 3 个主力物料分类 + ≥ 2 个人员分类） | < 50 条 = 录价太重，必须砍表单字段 |
| 供应商数 | ≥ 20 家 | 比价无从谈起 |
| 从系统出的报价单 | ≥ 10 份，且**所有对外报价 100% 从系统出**（含改版） | 0 份 = 出单没比 Excel 快，产品核心假设失败 |
| 单份报价单耗时 | 从改前约 3 小时降到 < 40 分钟 | 降不下来 = 勾选/算价链路有问题 |
| 查"上次这家做这个多少钱"耗时 | < 30 秒 | 搜不到 = 搜索或命名规范有问题 |
| `has_overdue_price` 为真的报价单占比 | = 0 | > 0 = 有硬失效价流出，是危险的报价事故（口径见 12.1） |
| 手填成本行占比 `manual_cost_line_ratio` | < 30% | > 30% = 价格库覆盖不足，用户主要靠手填，系统价值未成立（口径见 12.1）。前提「录价权限覆盖到实际拿价的人」**已由 Q8=(c) 满足**；冷启动首月只看趋势不考核 |
| **`found_but_not_used` 占手填总量比例** | **< 20%** | 库里有价但用户仍手填 = **纯体验问题**（搜不到/不会用），与权限无关。这是"产品好不好用"的诚实指标（12.1.1） |
| 周活跃用户 | ≥ 3 人 / 周 | 只有 1 个人用 = 没解决团队问题，只是个人笔记 |
| 每周新增/更新价格 | ≥ 10 条 | 库不增长 = 没有形成沉淀习惯 |

### 13.2 上线 3 个月的判断线

| 指标 | 目标 |
|------|------|
| 报价单价格复用率（新报价单里来自历史库的行占比） | ≥ 60% |
| 平均毛利率可见度（有毛利率记录的报价单占比） | 100% |
| 报价单改版率（version > 1 的占比） | 有改版说明客户真的在用系统出的单 |
| 因价格错误导致的返工/亏损事件 | 0 |

### 13.3 什么情况判定失败（要及时止损或重做）

- 4 周后价格条目 < 50 条 → **录价流程重做**，不是加功能。
- 报价单从未从系统出 → **出单流程重做**，不是加功能。
- 只有 1 个用户在活跃 → **权限/协作设计有问题**，加深色地判断是否需要"成员只能看不能改"之外的分工。
