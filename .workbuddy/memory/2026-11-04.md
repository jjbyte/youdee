## 项目：「有底」活动物料与人员供应商价格库 + 报价单系统（MVP 开发专家团 v2.1.0）

### 需求背景
客户为活动策划执行公司，痛点：物料（淘宝线上采购 vs 线下定做厂）与人员（自有管理 / 外聘专家 / 外聘兼职）在不同供应商价格差异大，价格散落微信/Excel/记忆里，下次报价想不起来历史价。要做内部网页系统，记录多供应商价格并快速拼出客户报价单（含成本毛利）。

### 客户已确认的 11 条口径（Phase 0 问答）
1. 范围：价格库 + 报价单生成（不做项目成本核算 / ERP）
2. 用户：公司内部 3-10 人共用，账号登录 + 管理员/成员两级
3. 价格能力：历史趋势 / 多供应商并排比价 / 有效期与阶梯价 / 图片链接附件，四项全要
4. 终端：电脑网页为主
5. 器材租买：**以租赁为主** → pricing_nature 默认值按分类继承（设备类 rental_per_day / 定做类 custom_made / 标品类 purchase）
6. 手机查价：**不是刚需** → 只读三档响应式，不做独立移动端
7. 审批：**不要审批，不要发出蠢单就行** → 发送前自检 7 warning + 1 blocker + 出单通知，无审批态
8. 含税：**报含税价** → tax_statement_default = inclusive
9. 录价权限：**谁都能新建，改旧价需管理员（c 分层开放）** → canCreatePrice / canOverridePrice 两函数分开，禁止合并
10. 毛利红线：**按项目类型分** → quotes.project_type（5 值枚举，可空）+ margin_thresholds 配置表，空值回退 25%
11. 分类：8 类物料 + 8 类人员，原样通过

### 待客户补充（不阻塞）
- Q1 高频物料单位折算系数（喷绘布 1㎡=?张、桁架 1根=?m、LED 1块=?㎡ 等）。不填则这些物料不标最低价，只并列显示 + "单位不同不可比"。

### 核心技术决策
- **PostgreSQL 18 是决定性选型**：唯一能用 `daterange` + `EXCLUDE USING gist` 在库层强制「同一主体×供应商×交易性质×税口径 的价格生效期不重叠」。MySQL/SQLite 只能应用层先查后插，并发下照样插重复，且不报错。
- 价格唯一键演进到**六元组**（item, supplier, pricing_nature, tax_included, pricing_mode(人员), 生效期区间）
- `pricing_nature` 必须 NOT NULL 且含 `service` 值（人员恒取）—— 若取 NULL，`NULL = NULL` 为假会让 EXCLUDE 约束对人员整段静默失效
- 价格版本化：改价 = 新增版本 + 旧版 effective_to 置为新价生效日前一天 + status=superseded，**禁止原地 UPDATE unit_price**
- 报价单行全量快照（`*_snapshot` + 金额列 NOT NULL 无默认值），item_id/price_id 弱引用 ON DELETE SET NULL
- 单位折算只有**乘法**（`base_unit_qty`：1 个比价基准单位 = N 个本价格单位），全项目不出现除法，防符号写反
- 比价三层分组：pricing_nature → tax_included → compare_state（comparable/converted/not_comparable），**存在但不可比的行一律保留并标记，绝不静默删除**
- 客户版 PDF 走 Server Component 服务端裁字段（成本数字不进浏览器 HTML），独立 DTO，不用 hideCost flag

### 三条跨角色的通用判断原则（值得长期复用）
1. **会报错的错误是安全的，不报错的错误才是危险的。** 凡"两个值都合法、都能算出数、但其中一个是错的"处，必须强制二选一或显式确认，绝不允许静默用默认值。
2. **凡是"存在但不可比"的行，一律留在列表里并标记，绝不静默删除**（否则用户以为供应商没报价）。
3. **屏幕上的折叠合并不能自动继承到导出**（PDF 没有悬停，PDF 上给独立列）。

## Phase 2 实现期（2026-11-04 下午）— 定点标度是这座系统的单点故障

一天之内，同一类 bug 出现了 **4 次**，每次都是"不报错、只是数字不对"：

| # | 位置 | 症状 | 根因 |
|---|---|---|---|
| 1 | `fmtAmount` 诞生前 | 合计 2000 元显示成 20 元 | 一个函数 `toMoneyString(v, scale)`，第二个参数到底是"输入标度"还是"输出位数"说不清 |
| 2 | `parseMoney` 解析 `base_unit_qty` | 比价页 80.4750，报价成本 80.5562 —— **同一个价两个数** | 系数是 numeric(12,6)，用 scale4 解析并**硬截断**（`slice(0,4)`） |
| 3 | `compare.ts` 数量 | `qty_priced` 放大 100 倍（18㎡ 显示 99.90 套），阶梯档位全错 | 数量用 `parseMoney`（scale4）解析后喂给要求 scale2 的 `qtyToPricingUnit` |
| 4 | `compare.service.ts`（后端） | 同上，同一处错误的镜像 | 同一个 API 被误用两次 |

### 定下的规矩（后续任何改动不得违反）
1. **函数名必须带标度**：`parseMoney(p4)` / `parseAmount(a2)` / `parseQty(q2)` / `parseRatio(r6)` / `fmtPrice` / `fmtAmount` / `fmtQty`。禁止再出现"标度靠参数传"的通用函数。
2. **超出目标标度一律 ROUND_HALF_UP，禁止截断**。`parseScaled` 是唯一实现。
3. **折算系数单独一个标度（6 位）**，因为 DB 是 numeric(12,6)。它不是金额也不是数量。
4. **累加必须用未格式化的定点值**，不许把行小计格式化后再 parse 回来累加（先舍后算）。
5. **验收不变式：同一个价在任何两个接口上必须是同一个数**。已写进单测（`applyConversion(3200,'0.055556')==177.7792` 且截断口径 177.6000 被显式断言为错）。

### 为什么单测没抓到 1、2、3
单测是我（实现者）自己写的，口径错误会连同错误一起被断言成"正确"。真正抓住它们的是**跨接口对照**（compare 的 80.4750 vs price-lookup 的 80.5562）和**后端工程师按 domain 单测口径反推**。教训：涉及金额的模块，必须有一个"两条独立路径算同一个数"的对照测试，不能只有单路径断言。

## 前后端边界：请求体键名不匹配 = 一整类静默失效
后端读 snake_case，前端发 camelCase → 返回 200、什么都没存。受害最重的是"切换税口径预览"（不可逆操作前给了错的合计）与"按毛利率重算选中行"（作用于全部行）。
修法：`src/lib/api.ts` 唯一出口做 `deepSnake`，与响应侧 `deepCamel` 对称。**只在边界转换，业务代码不感知**。
经验：前后端并行开发时，字段命名风格的差异不会报错，只会让功能"看起来能用"。集成验收必须真的点一遍每个写操作，并回读确认落库。

## 首次远端部署：`npm ci` 失败 = 死依赖引发的 peer 冲突（2026-11-04 17:20）

远端 CentOS 上 `docker compose build` 在 deps 层 4.6 秒就挂了：

```
Invalid: lock file's effect@3.20.0 does not satisfy effect@4.1.2
Missing: effect@3.20.0 from lock file
```

### 根因链（三层，逐层剥才看清）
1. `@hookform/resolvers@7.0.2` 把 `effect@^4.0.0` 声明为 **peer 依赖**（它支持十几种校验库，
   每个都列成 peer）。
2. `@prisma/config@7.10.1`（`prisma` 的传递依赖）要求 `effect` **精确 3.20.0**。
3. 两个 major 版本无法共存于同一位置 → npm 报 lockfile 不自洽。
4. 而 `react-hook-form` 与 `@hookform/resolvers` **全项目零 import**（表单全是受控 state），
   是 Phase 1 技术栈清单里列了、实现时没用上的死依赖。

### 修法
删掉这两个死依赖（`npm uninstall`），`effect` 自动降级为 `@prisma/config` 的嵌套依赖。
`zod` 同样零引用但不引发冲突，本次保留未删。

### 为什么本地完全看不出问题（这是重点）
| 环节 | 结果 |
|---|---|
| `npm install` | **容错强**，装完 node_modules 就对了 |
| `tsc --noEmit` / `vitest` | 全绿（依赖缺失不影响，因为没人 import） |
| `next build`（本机 Windows） | 通过 |
| 构建机 `npm ci` | **不容忍任何不一致**，直接 EUSAGE |

**`npm ci` 与 `npm install` 的容错差异，是"本地全绿、部署就炸"最隐蔽的来源之一。**
从此 `deploy/pack.sh` 内置 `npm ci --dry-run` 门禁：不同步就拒绝出包。

### 附带确认的三件事（避免下一轮再失败）
1. lockfile 必须含 Linux 平台二进制。已逐项核对：`@img/sharp-linux-x64`、`@next/swc-linux-x64-gnu`、
   `@tailwindcss/oxide-linux-x64-gnu`、`lightningcss-linux-x64-gnu`、`@esbuild/linux-x64`、
   `@embedded-postgres/linux-x64` 全部在册 —— 在 Windows 上生成的 lockfile 不一定包含它们。
2. 没有会在安装期联网下载的 postinstall：只有 `prisma` 的 `preinstall`（版本守卫），
   `sharp` 走 optional 预编译包，`embedded-postgres` 的 PG 二进制也是 optional 包。
3. 运行期不 import `@prisma/client`（数据访问全走 `pg`），所以运行层没有 `prisma generate` 的产物
   也不影响任何请求 —— 构建层与运行层的 node_modules 不是同一份，这点容易漏。

## 远端部署第三轮：NODE_ENV=production 吃掉 devDependencies（已修，0.1.2）

### 症状
第 3/6 步 `next build` 报 `Cannot find module '@tailwindcss/postcss'`（globals.css、design-tokens.css 两处）。

### 根因（与 CSS 无关）
`manual-deploy.sh` 用 `set -a; . ./.env` 把 `NODE_ENV=production` 导出了，
npm 见到它默认 `omit=dev`，**devDependencies 整包跳过**。
而 `@tailwindcss/postcss`、`tailwindcss`、`typescript`、`tsx` 全是 devDep。
`prisma` 没受影响是因为它在锁文件里没有 dev 标记（被生产依赖传递到了）。

**判据**：日志 `added 404 packages`。锁文件 prod=431 / dev-only=123 / total=554，
404 正是 prod-only 数量（差额是 Linux 上跳过的 Windows optional 包）。
以后再遇到"装少了"，先数这个数。

### 修法
- 第 1 步：`NODE_ENV=development npm ci --include=dev`（只改这一步的 NODE_ENV，运行期仍是 production）
- 装完立即校验 `@tailwindcss/postcss` / `tailwindcss` / `typescript` / `prisma` / `tsx`，
  缺了就在第 1 步退出，别让失败漂到第 3 步去猜

## 第五轮：我自己的校验函数写错了（0.1.4）

### 关键事实反转
远端输出 `ERR_PACKAGE_PATH_NOT_EXPORTED Package subpath './package.json' is not defined by "exports"`。
这说明 **`require.resolve('@tailwindcss/postcss')` 已经成功**，失败在下一行读版本号。
也就是说：**包一直是好的，Node 一直能解析到它**，0.1.2/0.1.3 的"依赖缺失"判断都是我自己引入的假阳性。

### 两个错误
1. 用 `require('@tailwindcss/postcss/package.json')` 读版本 —— 该包 exports 只暴露 `"."`，
   子路径必然抛 ERR_PACKAGE_PATH_NOT_EXPORTED。以后读第三方包版本一律走磁盘：
   先 `require.resolve(pkg)`，再从入口路径向上找 `package.json`。
2. 基于假阳性做了"自动单包补装"，在部署机上白改了依赖树（日志 `added 1 removed 1`）。
   已删除该逻辑：部署机上不自动改依赖，真解析不到就直接停并给出 `rm -rf node_modules` 指令。

### 因此 Turbopack 那个报错仍未定论
Node 侧解析正常，Turbopack 侧报 Cannot find module。可能是：
- Turbopack 的 `root` 推断（已显式钉 `turbopack.root = process.cwd()`）
- Turbopack/PostCSS 转换在特定版本的解析缺陷（webpack 路径正常，已实测）

处理方式改为工程化：Turbopack 失败 → 自动 webpack → 成功后写 `.build-via-webpack` 记号，
以后直接走 webpack 不再白试。诊断块增加「从 .next/build/chunks 解析一次」以区分解析根问题。

## 第六轮：部署成功，自检 19/20 —— 失败的是断言本身（0.1.5）

3. 每个不可比行 `warnings` 非空（灰化卡片上要有话说）

## 第七轮：公网 http 部署登录后立刻 40101（已修，0.1.6）

### 症状
浏览器用 admin/youdee2026 登录，"密码对、登录接口 200"，紧接着提示
`{"code":40101,"message":"登录已过期，请重新登录。"}`，进不去任何页面。

### 根因
`setSessionCookie` 里 `secure: process.env.NODE_ENV === 'production'`。
生产机是 `http://<公网IP>:3000`（无域名无证书），浏览器对 http 页面返回的
`Secure` Cookie **静默丢弃** —— 响应头照常收到，只是不保存。
于是登录后第一次 `/auth/me` 没 Cookie → 40101。
本地开发是 development，永远不复现；自检脚本自己把 Set-Cookie 塞进变量，也不复现。
**这类缺陷只有"真的用浏览器点一遍"或"直接读响应头"才能发现。**

### 修法
`cookieSecure()`：`COOKIE_SECURE=1|0` 显式指定 > `x-forwarded-proto` > `Origin` > 兜底 false。
clearSessionCookie 同样处理（否则清不掉）。生产 + 非 Secure 时打一条 warn（一次性），
提示传 `X-Forwarded-Proto` 或设 `COOKIE_SECURE=1`。

### 自检补的第 21 项
「会话 Cookie 能落到浏览器」：读登录响应的 `Set-Cookie`，目标是 http 而带 `Secure` 就判失败。
本地把它验成双向：正常配置 21/21；`COOKIE_SECURE=1` 故意配错时该项按预期失败。
这补的是自检的**结构性盲区**：脚本绕过浏览器策略，Secure/SameSite/Domain 这类问题它天生看不见。

### 判定顺序可复用
判断"Cookie 该不该 Secure"不能看 `NODE_ENV`，要看**浏览器到应用的这一段**是什么协议。
反向代理终结 TLS 时，代理必须传 `X-Forwarded-Proto`（nginx 示例已写进 docs/05-DEPLOY.md §5）。
